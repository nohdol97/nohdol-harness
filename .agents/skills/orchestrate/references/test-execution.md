# Test execution evidence — root AGENTS.md §13-2

Long-running commands, including full test suites, redirect stdout/stderr to per-run files under `_workspace/<task>/`; never overwrite earlier logs. Record command, cwd, revision/dirty state, completion status and exit code alongside each log. Read bounded ranges or search the file; display truncation alone never warrants rerunning the command. Missing or incomplete logs remain unverified, not successful. Preserve failure/timeout/cancellation/incomplete status; a log reader's exit code is not the test command's result. Keep root §3's secret and external-output rules.

For the same task, run the full suite at most once after changes and once at final verification, shared across host/workers/reviewers. Hand off consumed slots, command scope, code state and log paths; do not reset the count on fixes, task splitting or delegation. This is a cap, not a quota: do not run unnecessary full suites. Use targeted tests for intermediate repairs, TDD and independent reviewer reruns. Related-test reruns required by reviewer/team-review do not authorize additional full-suite runs. Coordinate ownership before launch so parallel reviewers do not each consume a slot.

If the final suite fails or later edits invalidate its evidence, repair and run targeted tests within scope; report the remaining full-suite validation as unverified. The two exceptions below are the only runs beyond the cap. Do not exceed the cap otherwise or claim completion using stale evidence. A failed, cancelled or timed-out full-suite attempt consumes its slot. Summary returns contain actual status, relevant results and original evidence paths. Existing safety, SDD/TDD and independent review requirements remain.

**Launch every full suite through the machine-wide slot limiter.** The per-task cap above says nothing about how many tasks run at once; several sessions on one machine each within their cap still stack (measured 2026-11-23: load 30–95 on 8 cores). Run `python3 .agents/hooks/suite-slot.py -- <suite command>` (root-relative path; from a worktree use the absolute root path). It lets at most 2 suites run machine-wide (`--slots N` or `SUITE_SLOTS` to change), waits for a free slot, and passes the suite's own exit code through. (Here a "slot" is a machine-wide concurrency permit; the cap's "slot" above means a counted run.) Slots are `flock` files in `/tmp/harness-suite-slots`, so a killed holder frees its slot and the suite's child processes keep it taken until they exit. Exit 75 (stderr: `no slot freed`), 64 (bad arguments or environment) and 71 (slot directory or command unusable) mean the suite **never ran**: that is unverified, not red, and it is not an attempt under spec R3, so the one-post-change and one-final counts are untouched. A killed suite returns 128+signal. Wrap a suite made of several commands (lint, typecheck, test, e2e) as one call, `-- sh -c '…'`, so one task holds one slot for the whole sequence. Run it in the background with redirected logs like any long command, because waiting for a slot can take as long as a suite; the log's first stderr line says `waiting`. Targeted tests are not wrapped. A nested call inside a held slot runs directly. Reason: running suites one or two at a time finishes each faster and removes the load-induced timeouts that discard whole runs; this is a gate on concurrency, not on the number of runs.

**The final run is on the tree that merges.** When the branch absorbs a newer `origin/main` after its final run (another session merged — `git rev-list --count <final-run commit>..origin/main` is non-zero at rebase or merge; record it), that run is stale evidence and the final run is repeated once on the merged tree, even when the merge has no textual conflict. Your own later edits are not this case. Measured 2026-11-23: a clean merge of a peer's docs-and-lint-rule change left 4 real failures (stale verbatim excerpts, a changed option schema).

**One deferred rerun for a load-only timing failure.** Classify every failure of a red full run first. If they are all timing-class — a test timeout (vitest `TestTimeoutError`, Playwright `Test timeout of Nms exceeded`) or an assertion that compares an elapsed time the test itself measures (a `Date.now()`/`performance.now()` difference) with a constant; read the assertion line, not the message — in test files that `git diff --name-only origin/main...HEAD` (plus `git status --porcelain` for uncommitted edits) does not list, and the 1-minute load average read during or right at the end of that run (saved next to the log) was above twice the core count (`sysctl -n vm.loadavg` and `hw.ncpu`; `/proc/loadavg` and `nproc`), the run decides nothing about the change. Wait in the background until the 1-minute load is below twice the core count (a bounded foreground loop where there is no background re-invoke, as in inflight-survey Wait and watch step 3; a user message ends the wait; give up after about an hour and report the suite unverified), rerun that suite once, and report both runs. This applies only to a red final run (the original or its repeat on the merged tree); a red rerun is reported unverified, with no further rerun. Any other failure, an ordinary assertion in an untouched file included, gets no rerun and is handled as above. Never raise a timeout or bound to get green. Reason: on 2026-11-23 several sessions testing on one 8-core machine drove load to 30–95; 5 s and 30 s timeouts and perf bounds failed in different files on many runs, and reruns passed once load fell below 15. At that load a red run carried no information about the change, and reporting it unverified would have blocked every merge that day.
