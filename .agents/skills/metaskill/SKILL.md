# metaskill — the skill that builds harnesses

## Why this skill

Building harnesses ad hoc gives every project a different structure, breaking routing, inheritance, and symlinks. This skill enforces that every harness shares the same skeleton (AGENTS.md single source, change history, ADRs — root: CLAUDE.md `@AGENTS.md` import + always-on anchors (ADR 021) + `.agents/` symlinks; sub-projects: centrally managed under `.agents/projects/<name>/`). Reason: a harness's value comes not from individual files but from **consistency** — an agent entering any project must find the same rules in the same place.

## Mode fork (first decision)

**Check carry-in before the fork.** If the project tree already has git history or a remote, or its registry row records a harness that is merely missing on this machine, it is a **carry-in** (scenario below) — not a new creation. Missing sub AGENTS.md is exactly the state new-creation tests for, so without this check the fork routes an imported repository into `references/scaffold.md` §2, which runs `git init` and a stack scaffolder over a tree that already has both.

Otherwise: if the target path **already has an `AGENTS.md` → improvement mode**; **if not → new-creation mode**.

- **Improvement mode**: Respect the existing structure. Fix only the defects instead of rewriting wholesale, and record every change in that AGENTS.md's change-history table. **When the change shifts an obligation, threshold, exemption, scope, or firing condition** (the same boundary common rule 8 uses), query the knowledge source first if REGISTRY.md records one (root AGENTS.md §7 clause 8) — harness design is exactly the area where the model's cutoff hides current practice, and this trigger fires with no project to route, so nothing else will open that section for you. For structural changes (pattern transition, 8+ agents, etc.) also leave an ADR. **Verification proportionality**: independent verification (reviewer) of harness changes scales with risk — **normative changes** (rules, procedures, gates, trigger boundaries, agent permissions, hook code) require independent reviewer verification; **non-normative diffs** (wording polish, pointers, typos, history rows — nothing that changes judgment or behavior) are covered by self-verification (reference/conflict check) + history record. Reason: if verification cost (~100k tokens and several minutes per run — measured: 2026-07-17 session, average of 6 reviewer runs) stays fixed regardless of diff risk, it becomes overconsumption relative to output (root §8 ④). **When judgment is ambiguous, lean toward verification** — a false pass is more dangerous than a false block (reviewer §2). **Two or more independent-review BLOCKs on the same change within one working session is itself a signal, not just a delay**: pause further round-by-round fix commits and consolidate the remaining scope into a spec (doc-writer template) or ADR before continuing — a same-evening chain of fix commits (measured: 2026-07-26 corporate carry-in boundary wiring, 3 BLOCK rounds over skill/doc edits in ~33 min; 2026-07-26 autoloop exit-watch, 4 fix commits over the exit-watch logic in ~48 min) means the design, not just the diff, was underspecified going in. A single BLOCK, or rounds spread across separate sessions, does not fire this. Pressure testing (common rule 7) applies only to newly created or revised behavioral disciplines — skipping verification/tests with proportionality as an alibi is exactly the "omitted code" that §16 forbids. **After completing a root-harness improvement**, report in chat what was improved and append one line `- YYYY-MM-DD [개선] <content> (PR/commit)` to `_workspace/harness-ops-log.md` (the ops log is user-facing — written in Korean) — the single place to check "what was improved" across sessions.

**That line states the verification decision, and there are three states, not two.** Name the verification that ran (rounds and verdicts — the existing convention); **or**, when you judged the change non-normative and ran none, say that you skipped it **and what made it non-normative**; **or**, when the change was normative and verification **could not run**, write `검증 불가` with the reason and what you tried. The third state is not a softer version of the second — the change still carries every obligation a verified one would, and the record has to say the round is owed rather than settled. Reason for the third: a session whose configuration forbids subagent dispatch cannot verify anything, and with only two branches on offer it will either say nothing or reach for "non-normative", which is the one wording that makes the omission look legitimate. Measured 2026-08-02: a gate change (`22ad409`) shipped with no independent reviewer for exactly that reason, and the fact reached the ops log only because the session volunteered it. Reason: the proportionality rule above is self-applied, and its judgment otherwise leaves no trace at all — afterwards a legitimate exemption and a silent skip look identical, so neither review nor the user can tell them apart. Measured 2026-07-29: two same-day improvement lines carried no mention of verification while every other line that day stated its rounds, and nothing in the record distinguished "judged non-normative" from "did not consider it". **This records the judgment; it does not authorize it** — a change that shifts an obligation, threshold, exemption, scope, or firing condition is normative whatever the line claims, and writing "non-normative" on one does not make the verification optional.
- **Interview-first owner (improvement mode only) — a harness change reaches no orchestrate gate (root AGENTS.md §13-0)**: `orchestrate` routes harness work away from itself (its description names metaskill), so the Phase 0-2 step that assigns an interview owner never runs here — **this session is the owner**. Before the first edit to a normative clause, put the question list in front of the user: the assumptions the change rests on, the sibling clause it could collide with (common rule 8), the forks you would otherwise resolve silently, and — because the change is normative — **whether the independent verification it requires can actually run in this session**. Ask that last one only when something makes it doubtful (a session instruction restricting subagent dispatch, a tool that is unavailable, no network), and ask it **here**, at the interview, not later: root §13-0 admits no mid-work questions outside §3 and data-loss confirmations, and a block imposed by the session's own configuration is one only the user can lift. If it cannot be lifted, the change still ships under the third ops-log state below — recorded as owed, not as exempt. **The ops-log line carries this judgment the same way it carries the verification one** — name the round that ran, or say there was nothing to ask and what made the request unambiguous. **The new-creation and carry-in scenarios are out of scope** — each already names its own single question point, and this clause does not re-open one. Reason: the two-BLOCK signal above fires only *after* a same-evening chain of fix commits, so the surface has a measured failure but no device on its early side; this clause takes that earlier firing point. What those two cases would have cost with an interview is **not** recorded — their must-fixes were sibling-collision and provenance defects (rules 8·9), and no record names a user answer as the missing input.
- **Install-site profile gate (mandatory before modifying any tracked harness file — root AGENTS.md §5)**: Check the install-site profile in REGISTRY.md. If **corporate**, do not modify tracked files at all; record the intended change in `_workspace/harness-updates.md` as a `대기` (pending) item (item format: under `## YYYY-MM-DD title`, status (대기/적용됨) / target files / change content / rationale — the change content must be detailed enough to apply as-is on the personal machine, ADR 012). If the profile is unrecorded, confirm with the user, record it in REGISTRY.md, then proceed (remote PR sessions are treated as personal). Untracked areas (`.agents/projects/`, REGISTRY.md, `_workspace/`) may be modified regardless of profile — they never touch git.
- **New-creation mode**: follow the procedure below.

## Clarification interview (mandatory before proceeding when anything is ambiguous)

If the project has any ambiguity, do not proceed — actively question the user: stack, deployment method, recurring tasks (record as skill candidates — creation is deferred). Reason: a harness built without an interview gets bypassed on first real use, and a bypassed harness never gets read again. However, **read project documents such as README before asking about role/purpose** (observation first), and **never ask about related projects** — they are filled in through real-work observation (root AGENTS.md §1).

## New-project creation scenario ("프로젝트 새로 만들어줘")

1. Clarification interview
2. Create directory & basic scaffolding → **see `references/scaffold.md`**
3. Create the harness (see "Deliverable requirements" below)
4. **Do not create skills/agents (deferred creation — root AGENTS.md §12)**: initial deliverables are documents only (AGENTS.md, adr/). Recurring-procedure candidates from the interview's "expected recurring tasks" answer and from the stack (build/test/deploy etc., see the candidate reference table in `references/scaffold.md`) are **only recorded in the sub AGENTS.md "skill candidates" section**. Actual creation happens solely via the "sub skill/agent creation scenario" below. Reason: skills made in advance diverge from real use and get bypassed — build only what proven need demands.
5. **Add a new row to the project registry in root REGISTRY.md** — role based on document/interview observation; related projects start as "미기록" (unrecorded — updated through real-work observation, root AGENTS.md §1)
6. Update the REGISTRY.md change history

Also update the registry on project **deletion/move**. A registry out of sync with reality skews all routing.

## Sub skill/agent creation scenario (deferred creation — the only creation path)

Trigger: **when a recurring task is observed, or a procedure/role appears mid-work that seems worth registering as a skill/agent** (including the 4 evolution-trigger signals). Procedure:

1. Propose the candidate to the user (no unauthorized creation). Items recorded in the sub AGENTS.md "skill candidates" section are first-priority candidates.
2. On approval, create at **`.agents/projects/<name>/skills/<skill>/SKILL.md`** or **`.agents/projects/<name>/agents/<agent>.md`** — `.agents/projects/` is untracked, so it never enters git. Format is identical to root (the "skill common rules" below in full, agent-rules.md 10 sections).
3. **List the skills/agents and their paths in the sub AGENTS.md** — this location is not auto-discovered by the CLI, so routing reading the sub AGENTS.md is the only path that loads them. Put the actual commands in the body (a skill without commands is worse than none).
4. Promote to root `.agents/skills/` (tracked) only skills that generalize across projects/install sites (after removing project-specific content).

## Project carry-in scenario ("사내에서 그 프로젝트 가져와줘")


> **This scenario's “carry-in/반입” means bringing a project *into this harness*.** It is a different concept, with different vocabulary, from transferring that project's output to a deployment site (`공용`/`배포처`, ADR 036). Never use this scenario to introduce `반입`·`사내` vocabulary or `docs/carry-in.md` into a product repository; that surface uses `docs/site-setup.md`, `docs/ownership.md`, and the `공용`/`배포처` vocabulary.
**Fires on the importing machine's own signals, never on the export-side section.** The 「배포처 이관 경계」 section is written by an export-side question ("do projects built *here* get carried into the company"), so at the importing site the honest answer is "no" and the section is legitimately absent — gating on it would make this scenario unreachable exactly where it runs. Fire on any of: the user asks to bring a project over; a project directory exists whose registry row records a harness — or 하네스 유무 `미확인` with 이관 not `로컬` — that is **not present on this machine** (both limbs of the §7 routing stop); or an incoming `.agents/projects/<name>/` arrives with no matching registry row, or with a row whose 하네스 유무 is `미확인` (the arrival is what resolves that state — see step 2).

Importing a project built on the other machine. **Not the same as new-project scaffolding**: the repository already exists with its history, so nothing is generated except the harness side. The reason this lives at root rather than in the sub-harness is ordering — the sub-harness is untracked, so at carry-in time it does not exist on this machine yet.

**Open with one batched interview — this is the scenario's single question point** (root AGENTS.md §13-0). Before step 1, ask together: ⓐ does a sub-harness for this project exist on the other machine, and if so how will it arrive; ⓑ does the corporate remote already exist, and at what URL. Neither is knowable from here (see step 2), and both are needed before the first irreversible action — step 1 wires a push target and step 2 decides whether any project rules load at all. Skip whichever question this session's trigger already answered — an arriving `.agents/projects/<name>/` answers ⓐ by itself — and look up what is discoverable here rather than asking it (`git remote -v` answers ⓑ on a repository already wired). **On re-entry to resolve a `미확인` row, only what is not already done applies**: the repository is here and the remotes are wired, so resume at step 2's copy-in and step 3's name alignment rather than replaying step 1, then steps 4 and 5 as usual — step 4 matters most here, because the sub-harness has just arrived and nobody has checked yet whether it carries the boundary section. Later steps do not re-open questions; if an answer does not come, take the branch that step names and flag it. **"Not yet — I'll create it and tell you" is an answer, not a missing one**: it is collected when the step that creates the thing produces it, which is not re-opening.

1. **Bring the repository.** The user moves it (clone from the personal remote where the network allows, otherwise an archive) and creates the corporate remote themselves — repository creation and pushing are externally publishing operations (root AGENTS.md §3). Wire two remotes by a fixed convention, so a later session reading this row knows which name means which side: **`origin` = corporate (the push target), `upstream` = the outside copy (pull only)**. One-way flow is what keeps the two copies from becoming rival originals.

   **Disable the outbound push mechanically** — "pull only" as prose lasts exactly until someone types `git push upstream`:

   ```bash
   git remote set-url --push upstream DISABLED
   ```

   Measured (git 2.39.5): `push` then exits 128 with *"'DISABLED' does not appear to be a git repository"*, while `fetch` and `pull` still exit 0. It blocks the accident, not an intent — anyone can unset it. Suggest it; the user runs it.

   **Repoint the branch after renaming, or a bare `git push` hits the block.** `git remote rename origin upstream` rewrites `branch.<name>.remote` along with the remote, so the tracking branch follows the *outside* copy even after a corporate `origin` is added — a plain `git push` then exits 128 on the DISABLED URL. It fails safe, but the corporate push the user actually wants is broken, and the obvious-looking repair is removing the guard:

   ```bash
   git config branch.<branch>.remote origin   # or: git push -u origin <branch>
   ```

   Measured (git 2.39.5, two remotes wired as above): bare push before the fix exits 128, after it exits 0; the explicit `git push upstream <branch>` still exits 128 and `git fetch upstream` still exits 0, so the guard is intact.

   **Wire only the URL the interview produced** (question ⓑ above). Guessing it from a naming convention and probing with `git ls-remote` is an acceptable fallback only after asking produced no answer, and the guess must then be **stated to the user and confirmed before it becomes `origin`** — a namespace-matching hit proves a repo exists at that URL, not that it is ours, and `origin` is the push target this step otherwise assigns to the user under §3. Never wire an unconfirmed guess.
2. **Carry the sub-harness across by hand.** `.agents/projects/<name>/` is untracked and has no remote recovery path (ADR 005), so neither a clone nor an archive of the *project* contains it — it lives in the *harness* repo, and only on the machine that made it. Without this step the session routes into the project with no project rules at all, silently. **The user copies it across by hand** — `AGENTS.md` at minimum, plus `adr/` and any lazily created `skills/`/`agents/`, into the same `.agents/projects/<name>/` path here. Create the directory first (`mkdir -p .agents/projects/<name>`); a machine that has never had this project does not have it.

   **Never infer its absence — that is interview question ⓐ.** The exporting site's REGISTRY.md is itself untracked and lives only on that other machine, so this session structurally cannot read it and cannot tell whether a sub-harness exists over there. Your own REGISTRY.md's silence is not evidence: that file was never in a position to record the other site's state. **A carry-in never ends with absence assumed** — every answer is routed and an unanswered one is recorded as unknown, not as none: *exists* → hand copy as above; *none over there* → say so and write it here via step 4, which already prescribes writing a missing one; *user cannot say* → record `미확인` in the 하네스 유무 column (never `없음`, per the registry's own 확인한 부재 ≠ 확인하지 않음 rule), flag it in the report, and say plainly that **the project stays under the §7 clause 2 stop until the answer arrives** — that clause fires on `미확인` exactly as it does on a recorded harness, so diagnosis stays open while Edit/Write/commit wait. Do not write a sub-harness here to escape the unknown: a guessed original collides with the real one when it lands. Reason: a session that guesses "no harness" routes into the project with every project rule and gate silently unloaded — the state root AGENTS.md §7 clause 2 treats as §3-class, and one that clause never catches because with absence recorded it does not fire. Observed 2026-07-27 (user report from the other install site): this exact miss happened on a carry-in where the sub-harness did exist and the user knew where it was.

   **There is deliberately no automated channel** (decided 2026-07-26 after a hosted-mirror attempt was withdrawn — ADR 006). Any always-available pipe between the two sides runs in the direction that carries corporate content outward as readily as the reverse, and no mechanical guard exists for it the way `set-url --push … DISABLED` guards the git path. Every rule written to make such a channel one-way collided with a rule already there. A hand copy has no direction problem because a person performs it. **Do not "fix" this by putting the harness file in the project repository** — that repo may not be ours: a repository joined inside the company can already carry someone else's `AGENTS.md` under active maintenance, and adding ours overwrites their convention or blends two conventions into one file (ADR 006, reason reinforced 2026-07-26). The manual step is the accepted cost of never touching a repo we do not own.
3. **Register in REGISTRY.md** — a row with 이관 = `배포처`, and the same 이름 as the sub-harness directory (routing resolves by that name); in the `미확인` branch of step 2, where no such directory exists yet, name the row after the project directory and keep the two aligned when the sub-harness lands.
4. **Verify the boundary section survived.** The sub AGENTS.md must carry the "where the work belongs" area map (see the scaffold reference). If it is missing — the project predates the boundary rule — write it now from the registry classification table and the repository's actual layout, because from this machine every edit to a file the other side owns is a future `git pull` conflict.
5. Wrap up: REGISTRY.md change-history row, sub AGENTS.md change-history row. On a 사내 profile the tracked harness files are not modified, so there is nothing to commit at root — the untracked additions are the whole deliverable.

**A step-4 edit made inside stays inside until the user carries it.** There is no channel to push it back (see step 2), so say plainly in the report that the outside copy is now behind and name the file — otherwise the two copies drift with nobody aware. The change-history row from step 5 is what the other machine compares against, which is why it is written even though nothing automatic reads it.

## Pending-queue application scenario (personal install site — "하네스 업데이트 적용해줘")

The path for actually applying improvement items carried over from a corporate install site on a personal install site. Trigger: the user supplies queue content (paste/file copy), or `대기` (pending) items are found in `_workspace/harness-updates.md` (including via harness-review integrity checks).

1. Confirm the profile is **personal** (corporate cannot run this scenario — items stay in the queue).
2. Review each item's target files/change content and apply — if the file has diverged since recording (already applied, target section changed), do not apply verbatim; translate the intent to the current structure, and confirm with the user when judgment forks.
3. Finish per the usual rules: update the file's change history, ADR for structural decisions, commit & push (§5), append an `[개선]` item to the ops log (`harness-ops-log.md`).
4. Update applied items' status to `적용됨` (applied, + application date) — the queue becomes history and prevents double application. **Reversing that transition is not a status edit alone**: when a later independent review finds drift, partial application, or a reversion, revert the status to `대기` and, in the same edit, append a line to `_workspace/harness-ops-log.md` saying why (`[개선]` or `[발견]`). Otherwise the ops log still reads as though the item settled, the next review rediscovers the same gap from scratch, and a close→reopen cycle that repeats has no way to surface as signal ②. The ops log is an application history, not a second queue — the status lives in `harness-updates.md` and only the reason goes in the log. **This holds wherever the reopen is decided**, including a site that never runs this scenario; it lives here because step 4 is the transition it reverses.

## Deliverable requirements (must be included in a new harness)

- **Root harness only**: `CLAUDE.md` has first-line **`@AGENTS.md`** import (always-on injection of the full single source at session start — ADR 021) + Claude-only **always-on anchors** (`## Harness: {domain}` section + **output language** + **routing summary** (skill names such as orchestrate) + **skill priority**). **No change-history table in CLAUDE.md** (root change history lives in `docs/harness-changelog.md`). Do not copy full rules into CLAUDE.md — only one-line top-priority anchors per turn (re-bloat prevention — root AGENTS.md §11). **Do not create CLAUDE.md for sub-projects** — no session ever starts at that path, so it is a dead file with no loader (root AGENTS.md §12).
- **When installing the root harness on a new workspace**: always create `REGISTRY.md` (install-site-specific project registry — untracked by git). Follow the `harness-install` skill. Never create one for sub-project harnesses.
- First line of `AGENTS.md` states inheritance from the root AGENTS.md (sub-projects). **Sub-project AGENTS.md** has a change-history table at the bottom (initial 1 row). **Root AGENTS.md separates change history into `docs/harness-changelog.md`** (ADR 021 — it is always-on injected via `@AGENTS.md`, so the audit log is removed from the import footprint).
- **Root harness only**: shared directories `.agents/agents/`, `.agents/skills/` + `.claude/agents`, `.claude/skills` symlinks. If symlinks are impossible in the environment, substitute a sync script and record it in an ADR.
- **Sub-project harnesses use central management (root AGENTS.md §12, ADR 006/007)**: create the original and only copy at root `.agents/projects/<name>/` — composition: `AGENTS.md` (including a "skill candidates" section), `adr/`, and lazily created `skills/`/`agents/`. `<name>` must match the REGISTRY.md registry row. **Never place harness files in `project/<name>/` or its git repository** (including symlinks/copies) — routing (REGISTRY.md → read the original) makes the connection, so no distribution mechanism is needed. `.agents/projects/` is install-site data and untracked.
- **Sub-project skills/agents are lazily created** — the "sub skill/agent creation scenario" above is the only creation path. No initial creation. If a hook is needed, put it only in root `.claude/settings.json` as a path-branching hook.
- **Agent/skill files must be created in the `.agents/` originals — `.claude/` is a symlink, so never create directly under it.** When a root agent is created/renamed/retired, synchronize the thin `.codex/agents/<name>.toml` adapter in the same change (do not duplicate the role body — only preload the full Markdown, ADR 027). If a symlink is replaced by a real file or a Codex adapter drifts, the two CLIs see different roles (root AGENTS.md §11).
- orchestrate integration: state that implementation/multi-step work passes root orchestrate's team-necessity judgment (Phase 0-1), and multi-project/team work forms teams via orchestrate (ADR 010).
- ADR directory (NNN-title.md on structural decisions): root harness → `docs/adr/`, sub-projects → `.agents/projects/<name>/adr/`.
- **Document map (MOC) sync (root harness only)**: when an ADR, spec (`docs/specs/`), or proposal (`docs/proposals/`) is created at root or changes state (superseded/implemented/rejected), **update the corresponding row in the `docs/README.md` index in the same commit** (root AGENTS.md §6). Same reason as the REGISTRY.md update obligation — an index out of sync with reality loses trust as a navigation basis.
- **Root README.md asset-list sync (root harness only — repeated-omission spot)**: when a skill/agent is **created, renamed, or retired** under root `.agents/skills/`/`.agents/agents/`, **update the root `README.md` directory tree (one-line skill/agent description list) in the same commit** — this list update was repeatedly missed when adding new skills (signal ②; changelog 2026-07-16 and 07-18 "README stale sync" are traces of after-the-fact resyncs). The MOC above (`docs/README.md`) is the ADR/spec/proposal index while **this tree is the skill/agent list — separate files**; confusing them and updating only one leaves the other stale. Sub-project skills/agents update **the list in the sub AGENTS.md** (§12), not the root README.

- When creating a skill, follow the "Skill common rules" below.

## Skill common rules (apply to every skill in this workspace)

1. **frontmatter is mandatory (spec violation makes the skill appear with no description)**: SKILL.md must start **from line 1** with `---` YAML frontmatter containing `name` (matching the directory name) and `description`. The CLI reads **only the frontmatter description** for listing and automatic trigger matching — a description written only in the body shows the bare name and fails to catch user input. Write the description as a single line; if the value contains YAML special characters such as colons (`: `) or quotes, **wrap the whole value in double quotes** (otherwise the entire frontmatter fails to parse). **Verify right after creation**: check line-1 `---`, the closing `---`, and description presence with `head -6`, **and the description byte length against the ~1024-byte CLI hardcap** (e.g. `grep -m1 '^description:' SKILL.md | wc -c`; keep margin — `wc -c` counts Korean characters as 3 bytes each). Reason: rule 2 states the length target but without a creation-time check it is only caught after the fact (measured: wrapup description shipped at 1410 bytes and needed two trim round-trips, 2026-07-19).
2. **description (English, concise, CLI hardcap ~1024 chars; Pushy routing elements stay)**: include ① verbs ② explicit trigger situations ③ **`Re-run:` keywords**, including Korean phrases that match user wording ④ **`Not for …` boundaries** where adjacent skills overlap. Keep mechanics in the body, not metadata. After any edit, verify both the individual hardcap and integrity R19's **9,000-byte aggregate catalog budget**; a new description that exceeds the remaining aggregate budget must compact existing duplicates in the same change. Negative boundaries outrank brevity because they prevent costly misrouting, but examples and rationale belong in the body. Reason: descriptions are loaded for discovery on every prompt, while the body is lazy-loaded only after routing.
3. **Progressive Disclosure**: SKILL.md body within 500 lines. Split into three layers — metadata → body → `references/` — and move conditional detail into `references/`. Reason: the longer the always-read body, the higher every invocation's cost and the more the core rules get buried.
4. **Why-First**: Do not list rules alone; include the reasons. Attaching a reason widens a rule's applicable range — the LLM can keep judging in edge cases.
5. **with/without**: State the difference with/without this skill (metric evaluation) at the bottom of the skill.
6. **Effective timing**: Skill additions/edits take effect **from the next session** (the CLI loads at session start). To use a just-created skill immediately, open a new session or invoke it explicitly with `/skill-name` — include this fact in the creation completion report.
7. **Pressure testing (behavioral disciplines only — ported from superpowers writing-skills, ADR 022)**: For discipline skills/rules that aim to change the model's default behavior (gates, prohibitions, forced procedures), do not declare completion from the static checklist alone — **first observe a pressure scenario (baseline) where a subagent actually violates without the skill**, write the skill targeting the rationalization phrases observed there, then confirm the same scenario turns into compliance (observe failure → write → confirm compliance — the documentation application of root AGENTS.md §13 TDD). If new rationalizations appear during confirmation, plug those holes and re-confirm. Reason: a rule that has never seen baseline failure blocks imagined violation points, not real ones. **Reference/procedural skills (command collections, templates) are out of scope** — for documents with no 'behavior' to resist pressure, this procedure is pure cost (root AGENTS.md §16 minimalism).
8. **Clause-collision pre-check (adding to or revising an existing block)**: **Fires when the target block already holds one or more clauses and you either add a clause or revise one so its meaning changes** — writing a new file or deleting a clause does not trigger it, and neither does wording polish. **Polish means no obligation, threshold, exemption, scope, or firing condition shifts meaning; if any of those does, it is a clause addition regardless of how small the diff looks.** Before drafting, enumerate ① the block's current clauses and ② every pointer that references the block (other skills, agent definitions, `CLAUDE.md` anchors, the Korean views). Then state, for each new or revised clause, **(a) which existing clause it could contradict** and **(b) what makes it fire** — the concrete situation that satisfies it and the situation that violates it. A clause with no statable firing condition, or one satisfiable in a way that voids its own purpose (an exemption broad enough that the rule never applies, a taxonomy that reclassifies violations out of scope), is not ready to ship. **This precedes reviewer verification and never substitutes for it** — normative changes still require independent verification per the improvement-mode proportionality rule above. Distinct from rule 7: rule 7 asks whether a new discipline targets *real observed* violations, this rule asks whether it *coheres with rules already present*. Reason: measured baseline — of the 8 must-fix items across two reviewer rounds on `branch-workflow` finish 4 (2026-07-26), 4 were exactly this class: a new clause colliding with a sibling clause in the same step (F1, D2), a taxonomy that rendered its own threshold rule unfirable (D1), and a delta path violating a floor set two clauses earlier (D3).
9. **Claim provenance (checkable assertions about anything outside the file you are editing)**: **Fires when a new or revised clause states something that could be checked and found false** — another tool's or CLI's behavior, another skill's or agent's clause, a file/directory structure, a command's output — **including when the statement rides inside a prescription** ("use X to do Y" asserts that X does Y). Checkability is the operative test: a clause does not escape by being phrased as an obligation. For each such statement the draft must name its evidence — the command actually run, or the file path plus section actually read. Record it in the change record (change-history row, commit message, or proposal), **not inline in the clause**, which would inflate an always-loaded body (rule 3, root §16). **The change record leaves the repository**, so §3 and root §7 clause 8 still bind: where the source itself may not be quoted outbound, record that the check was made and what it settled, without the identifiers. A statement with no nameable evidence is not ready to ship, exactly as under rule 8. Distinct from rule 4: rule 4 asks *why the rule exists*, this asks *how you know the stated fact is true*. **Precedes reviewer verification and never substitutes for it.** Reason: measured baseline — the `harness-install` jq clause (2026-07-26, `6307e28`) satisfied rule 8 and still drew a reviewer BLOCK of 1 must-fix + 5 should-fix (verdict and report path recorded in this rule's own change-history row). **Two** of those six were external-fact defects that one command or one file-open would have caught: `rtk json` described from assumption instead of from `--help` (it is a file reader, not an output filter), and the need for `~/.claude.json` reads attributed to tool-audit/harness-review when both skills prescribe agentsview instead. The other four were scope, contract, and generalization defects that this rule does not target — claiming more coverage than two would be the same unchecked assertion the rule exists to stop.
10. **English-first authoring (ADR 030)**: New harness assets (AGENTS.md files, agent definitions, SKILL.md, references) are **authored in English by default** — they are model-loaded assets, and English cuts input tokens on every load (root §15 rationale applied to load frequency). The Korean summary views (`.agents/agents/README.ko.md`, `.agents/skills/README.ko.md`, `AGENTS.ko.md`) **must be updated in the same commit** whenever their source assets are created, renamed, or retired — a stale summary view misleads the user the way a stale REGISTRY.md misleads routing. This is part of the completion checklist below.

11. **Change-record coverage (mechanical, before committing a harness change)**: the change-history row's 대상 column must name **every path the change touched**. Run it rather than recall it — `git status --porcelain` for work still uncommitted, `git diff --name-only <base>..HEAD` once it is committed. **Neither shows a gitignored path**, so add by hand the installation files you edited (`REGISTRY.md`, `.agents/projects/**`): the operative split is ignored vs not, not tracked vs not, and the ignored ones are exactly what a memory-based list drops. **When the change also carries an ADR, its 영향 list is a change record too and gets the same check** — a review round has already caught that list short. One exemption, and it is narrow: a record may omit **itself** — the changelog row need not name `harness-changelog.md`, the ADR need not name its own file. The few rows that do name it are ones whose *subject* was that file, which is the exemption not applying rather than an inconsistent convention. Anything else missing is a defect, including a file you edited in a round you are no longer thinking about. Reason: measured — in one change (2026-07-28, `vault-write`) the 대상 column omitted the always-on root single source after it was edited in an earlier round, and the same class recurred four times in that chain; a `git status` comparison would have caught every instance. Distinct from root §5, which requires the row to *exist*; this requires it to be *complete*. Distinct from rule 9, which checks assertions about the world outside the file; this checks the record of the change itself.

12. **Fix completeness before claiming a change is complete**: **enumerate the change's constituent sites first, then confirm each one individually** — by `grep` for the predicate you changed, or by opening the file — and only then claim completeness or ask for the delta round. State any site you decided not to change and why. Two firing points, because the failure is the same shape from either side: **applying a reviewer's must-fix items**, and **retiring or replacing a term, label, or predicate that lives at more than one site** — the second fires on your own claim, at the moment you would write 전 지점·모두·잔존 0 or any other word asserting exhaustive replacement. On that second path, three things decide whether the claim can be made at all:
    - **Write the retired-form list before sweeping** — singular and plural, English and Korean (harness rules are English with a Korean view, so a retired form exists in both by default), hyphen and spacing variants, and the compound words the term sits inside. **"잔존 0" speaks only for the list you wrote**; a zero found with a narrower set is reported as scoped, not as zero.
    - **Write the surface list too, and include the three that a tracked-file sweep structurally misses**: gitignored harness files (`REGISTRY.md`, `.agents/projects/**` — the same trap rule 11 names for the 대상 column, on the sweep instead of the record), **generators** (instructions that emit other files, which keep reproducing the retired form after every reader has been fixed), and **runtime strings** with the tests asserting on them.
    - **When the retired form is a homograph of one you are deliberately keeping, "0 hits" is not a criterion you can run at all** — most hits are legitimate and the residual hides in them. Write the preserved set down *before* sweeping, then the criterion becomes **every hit classified as retired or preserved**. **A multi-part finding is the default, not the exception**: reviewers name one symptom, and the same predicate usually lives at two to six sites (a rule, its Korean view, a generator that emits it, a change record, an ADR, a summary table) — two, an English rule and its Korean view, is the single most common shape. Reason: measured — across two review chains on one skill (2026-07-28), a fix landing at some sites but not all appeared in **7 of 9 rounds**, twice *inside the very line being edited*, and once as the implementer fixing one finding and recording it as a different one. The second firing point carries its own count: the same failure recurred **five times** on term retirement — the four the memory note `term-revision-sweep-all-sites` records (its originating case plus three logged recurrences, the last two dated 2026-08-02) and one more on 2026-08-03 — each time escaping the previous round's prescription along a different axis — path, language, term-set completeness, and finally homograph classification — which is why the three bullets are separate criteria rather than one instruction to sweep carefully. A memory note warned on four of the five and stopped none, so the check has to be the rule rather than the recollection. This does not mandate extra rounds; it makes the round you were already going to request test something new. Complements root §13-2 from the other side: §13-2 says do not take a subagent's claim on trust, this says do not take **your own** completion claim on trust.

13. **Rebuttals are judged at the state the finding was raised against**: concluding that a finding is a false positive is a claim about the reviewed artifact, so check it against **that** artifact, not against the tree as it stands after your later edits. This covers findings from any review or check — an independent reviewer, a daily or weekly `harness-review`, an integrity run — because the failure is in how the rebuttal is grounded, not in who raised the finding. (Measured 2026-07-29: the recurrence that escaped after this rule shipped was a rebuttal of a *daily-check* finding, which the reviewer-only wording did not reach.) Two cases, because **the reviewed state is usually uncommitted** — harness review runs on the working tree, and git offers no revision syntax for it:
    - **Raised against a commit** → `git show <commit>:<path>`.
    - **Raised against the working tree** → use the finding's own quoted evidence. A reviewer report carries `file:line` per root §4; a daily or weekly check records what it read in `harness-ops-log.md`. Either way that record *is* the state, so compare your rebuttal against it, not against the file now.

    If neither is available, say the finding is unresolved rather than dismissing it. Rebutting remains legitimate and necessary: reviews and checks do err, and a rebuttal that survives this check stands. Reason: measured — twice on 2026-07-27 a reviewer's finding was dismissed as a false positive on the strength of a current-tree `grep`, when the line genuinely had not existed at review time; both were caught later by a delta round. Same failure family as root §5's verify-before-asserting (present state used to settle a question about another state) but a different firing point: §5 enumerates merge, deploy, GitOps, issue, and pipeline surfaces, and the review loop is none of them.

14. **The record's own claims are checked too** (mechanical, while writing it): rule 9 sends evidence *into* the change record and rule 11 checks one of its columns, so the 사유 column — where counts, enumerations, and characterizations of other files are actually written — is governed by nothing. Two checks, because the failures split cleanly in two:
    - **Re-run, then compare against both the number and the list.** Every figure and enumeration you write is produced by a command run *while writing it* — never copied from a reviewer report, a subagent return, or your own earlier round, and never carried over from before your last edit. Compare the output to the count word **and** to the items you listed: "인접 절 3건" is counted from the three that follow it, and an `only`/`뿐`/`만` file list comes from `git show --stat` or `git status --porcelain`, not from memory of what you edited. **Re-run once more after the row is saved whenever the row itself would match the command** — a row citing `grep` for a marker becomes a hit for that grep. **The exclusion unit is the record file, not your row** — sibling rows have been citing the same marker for as long as the file has existed, so "excluding this row" leaves them all in and still does not reproduce. Exclusion fixes the *scope* and pinning fixes the *state*, and neither substitutes for the other, so do **both**: exclude the record file and say in the row that you did, and pin the figure to a real object name (`git grep <pattern> <commit> -- <paths>` — `HEAD` and branch names move, so they are not pins). Where the target cannot be pinned at all because it is gitignored, date the figure and say it is state-dependent.
    - **A characterization of another document is a read, not a measurement.** "모두 X 의미로만 인용", "그 스킬은 Y를 금지한다", "그 절은 Z를 요구한다" — open each site and read the sentence. `grep` establishes that a string is present; it never establishes that the surrounding text means what you wrote.

    Whatever you cannot check from this repository (a corporate-site event, another machine's queue, a session transcript) is marked unverifiable **in the record itself**, naming the path you tried — an uncheckable claim stated flatly is indistinguishable later from a checked one. Reason: a 2026-07-29 sweep of the change record found this class recurring through the last four days of harness changes and concentrated in 사유 rather than 대상 (its tallies are a classification, not a command output — the changelog row carries them with that marking and the report path). Two instances re-measured directly: a changelog rebuttal asserting "인용된 문자열은 파일에 없다(`grep` 0건)" for a string `grep -c` returns **3** for, one of them the cited commit's own ops-log line — that rebuttal narrowed the evidence base of the rule shipping in the same commit; and a row in the immediately preceding commit whose own stated `grep` did not reproduce even though it had already excluded itself — four sibling rows dated 07-14 through 07-26 were citing the same marker, which is how the exclusion unit above came to be the file. Rule 9 caught neither: a citation survives a measurement that was mis-read, run before the last edit, or scoped short, so this rule requires the **output**, not the citation. Distinct from rule 11 (paths in 대상) and from rule 12 (a fix landing at every *site*; a count word governing a list is not a site, which is how four of these reached a third review round).

15. **Justifying-case check (while drafting a new or revised firing condition)**: Fires when you **draft** a clause, gate, script predicate, or hook check that is new, or whose firing condition changes — **discharge it before the change is committed or sent for independent review**. The due point is drafting, not shipping: a device that is drafted, reviewed, and withdrawn has already spent the round this check exists to save. That device list is rule 8's boundary widened past "an existing block" — the near-miss below was a script predicate, which rule 8 never reaches. **Clauses that impose no obligation on anyone — pure reference or description — are out of scope**, as under rule 7; new-creation mode ships many of those and no measured failure can exist for each. **A clause requiring someone to do or record something is in scope even where it blocks nothing** — the 07-30 case below is exactly that shape, so a carve-out keyed to allow/block effect would exclude the rule's own evidence. Do three things and record them in the change record: ① **enumerate the occurrences you are citing as justification and run the drafted condition against each one** — the predicate against that case, or the case opened and read for whatever the clause keys on; ② **confirm the governed surface carries at least one measured failure**, since a surface with zero is one the clause polices only in imagination — this is a floor for shipping and **not a substitute for root §8's signal threshold**, which still governs whether the rule may be created at all; ③ state both results. **A justifying case the draft does not fire on is not a justification** — it is evidence the condition is keyed to the wrong thing, and what gets fixed is the condition, not the case list. Distinct from rule 7, which observes a *new* pressure scenario and covers behavioral disciplines only; this compares *already-cited* cases and covers any device carrying a firing condition. Distinct from rule 8, which asks whether a clause coheres with its siblings: rule 8 makes you **state** the firing condition, this one **runs** it. **Precedes reviewer verification and never substitutes for it.** Reason: measured three times, and in every one the mis-keying was found by a later round rather than by the author drafting the condition. The escape that item ② keys on is rule 13 itself — it shipped in `19d3d96` worded for reviewer findings only, and a rebuttal of a *daily-check* finding escaped it until `2a6fe3b` widened it. Two near-misses establish the frequency: `acf3bb4`'s predicate ("the cell carries no commit hash") does not fire on `c66e5f6:158`, the very case cited to justify it, because that cell cites six commits — caught by the author's own pre-implementation measurement; and the clause withdrawn on 2026-07-30 was keyed to `[개선]` lines while its justifying case `acf3bb4` carries a `[검토·기각]` line instead — caught by independent review.

> Rules 11-15 exist because the judgment they replace is not one this model reliably makes unaided — each names a command whose output settles it, or (rule 15 ①) a case to open and read. Prefer that shape when adding to this block: a rule that can only be *believed* to have been followed is one that will be reported as followed.

## Evolution triggers (automatic conditions that invoke this skill)

The 4 signals of root AGENTS.md §8 — ① same request type 3+ times ② same failure 2+ times (including same correction 2+) ③ observed harness bypass ④ shrink/efficiency (skills/agents unused 3+ weeks, token-overconsumption pattern 2+ times — weekly check only) — when detected, **propose** creation/improvement/**retirement/consolidation to the user**, and execute with this skill on approval. No unauthorized creation or retirement: the harness is the user's operating asset.
