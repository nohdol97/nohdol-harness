# ADR 035 — 하위 프로젝트 작업의 worktree 선행 생성과 정리

- 날짜: 2026-07-29
- 상태: 활성
- 관련: ADR 002(저장소 분리), ADR 005·006(하위 하네스 미추적·중앙 관리), ADR 022(superpowers 채택 — `using-git-worktrees` 기각), ADR 032(컨텍스트·출력 경제)

## 배경

`branch-workflow`는 "묵은 브랜치 위에서 시작해 머지 시점에 충돌이 몰린다"는 반복 실패를 막으려고 만들어졌고, 그 처방은 **절차**였다 — `checkout main` → `pull --ff-only` → `checkout -b`. 절차이므로 매번 지켜야 하고, 지켜지지 않는 경로가 실제로 관측됐다. 스킬 본문이 이미 그 흔적을 갖고 있다: 세션 재개나 `/model` 전환 직후 조용히 main으로 돌아와 있어 직커밋 직전에 잡힌 사례(2026-07-22)를 막으려고 `git branch --show-current` 재확인 조항이 붙어 있었다. 공유 체크아웃 하나를 브랜치 사이로 옮겨 다니는 구조가 그 실패의 토대다.

같은 구조가 다른 조항도 만들었다. 시작 절차 1단계는 `project/<이름>/`에 미커밋 변경이 있으면 **정지하고 사용자에게 묻는다**. 이유는 `checkout main`이 남의 작업일 수 있는 변경을 움직이기 때문이다 — 즉 정지의 원인은 위험 자체가 아니라 **브랜치 전환이라는 수단**이었다.

사용자 요청(2026-07-29)은 "`project`에 있는 것을 작업할 때 worktree 먼저 만들고 시작, wrapup 할 때 정리"였다.

## 결정

하위 프로젝트에서 **파일을 바꾸는 작업**은 전용 worktree에서 시작한다. 정리는 머지 실측을 통과한 것만 제거한다.

1. **발동은 쓰기 작업에만.** 진단·상태 확인·탐색 같은 읽기 전용 작업은 `project/<이름>/`에서 그대로 하고 worktree를 만들지 않는다. 읽기 전용 진단이 첫 제품 Edit로 바뀌는 지점은 이미 orchestrate 게이트 재진입 지점(§7 3항)이므로, 그때 이 절차가 돈다.
2. **위치는 `project/.worktrees/<프로젝트>/<브랜치>/`.**
3. **세션 cwd는 루트에 그대로 둔다.** worktree는 절대경로로만 접근한다(`git -C <worktree>`).
4. **생성은 `origin/main`에서 직접 분기**한다 — `worktree add <절대경로> -b <type>/<설명> --no-track origin/main`. main 체크아웃을 갱신하거나 전환하지 않는다.
5. **정리 판정의 정본은 `branch-workflow`**, `wrapup`은 세션 스윕 시점에 그리로 위임한다. 제거 조건은 ① `gh pr view --repo <owner/repo>`로 머지 실측 ② `git worktree remove`가 `--force` 없이 성공, 그리고 §3 사용자 확인 1회.
6. **서브에이전트에 위임할 때는 발행 프롬프트에 worktree 절대경로를 담는다** — `orchestrate`의 7요소 CONTEXT에 「작업 위치」를 추가해 규칙의 자리를 만들었다.

## 사유

**절차를 구조로 바꾸는 것이 핵심이다.** worktree를 `origin/main`에서 만들면 "최신 main에서 시작했다"가 지켜야 할 규칙이 아니라 **생성 명령의 결과**가 된다. 그리고 worktree는 브랜치를 하나만 쥐므로, 재개 후 main으로 되돌아갈 대상 자체가 없다 — 2026-07-22 사례를 막으려던 재확인 조항이 그 경로에서는 발동할 필요가 없어진다. 조항을 지우지는 않았다: `project/<이름>/`에서 직접 편집하는 경로가 남아 있고, 그때는 여전히 유효하다.

**미커밋 정지 조항이 완화된 것은 규칙 완화가 아니라 원인 소멸이다.** `worktree add`는 기존 체크아웃을 건드리지 않는다. 정지의 근거였던 "남의 작업이 움직인다"가 성립하지 않으므로 정지도 성립하지 않는다. 대신 남은 변경을 한 줄로 보고하게 해 망각은 막았다.

**cwd를 옮기지 않는 이유(사용자 판단, 2026-07-29).** 초안은 `EnterWorktree`로 세션을 옮기는 쪽을 권했고, 사용자가 크로스 프로젝트 작업을 근거로 반박해 뒤집혔다. 근거는 성립한다 — `EnterWorktree`는 세션을 한 저장소의 worktree에 묶고, 다른 worktree로 전환하려면 **같은 저장소의** worktree여야 한다(도구 계약). 여러 프로젝트에 걸친 수정은 첫 프로젝트의 worktree에 갇히고, 부모 cwd를 물려받는 서브에이전트도 함께 갇힌다. 루트 유지는 §12의 "모든 세션은 루트에서 시작" 전제와도 정합하며, 하네스 로드를 상위 디렉토리 `CLAUDE.md` 탐색이라는 부수적 메커니즘에 의존시키지 않는다. 대가는 명령마다 절대경로가 붙는 것이고, 이는 실비용이지만 갇힘과 달리 되돌릴 수 있다.

**위치 세 부분이 각각 근거를 갖는다.** `project/`는 gitignore 대상이라(REGISTRY.md 경로 규약) 루트 저장소가 깨끗하게 유지된다. 앞의 점은 `project/*/` glob을 쓰는 프로젝트 스캔에서 제외시킨다. 그리고 `_workspace/` **밖**이라는 점이 결정적이다 — 주간 하우스키핑이 14일 경과 `_workspace/` 디렉토리를 삭제 후보로 올리므로(changelog 2026-07-18), 거기 두면 미커밋 작업을 쥔 worktree가 그 목록에 오른다.

**ADR 022의 worktree 기각과 충돌하지 않는다.** 그때 기각한 것은 superpowers의 `using-git-worktrees` 스킬이었고, 기각 근거는 "Claude Code 네이티브 격리(Agent `isolation`)로 충분하다"였다 — 즉 **병렬 에이전트 격리** 축의 판단이다. 이번 것은 병렬이 아니라 단일 작업의 브랜치 격리이고, 네이티브 `isolation: worktree`는 발행 1회 동안만 사는 임시 worktree라 피처 브랜치를 며칠 쥐는 용도로 쓸 수 없다. 지식 소스 조회(§7 8항, 실시 2026-07-29)에서 얻은 축도 같은 방향이었다 — 수집된 3건이 모두 worktree를 **병렬 실행 격리**로 쓰고 있어, 이번 도입이 그 주류 용법과 다른 축임을 확인했다(큐레이션 노트는 근거가 아니므로 판단에만 반영, 인용 없음 — 사용 계약 1·2항). 그래서 두 종류는 공존하며, 스킬 본문에 "한쪽 규칙으로 다른 쪽을 정리하지 않는다"를 명시했다.

**`gh`에 `--repo`가 붙는 이유(독립 검증 F1).** `gh`는 cwd로 대상 저장소를 정하는데 이 설계의 cwd는 루트 하네스다. 한정자 없이 부르면 하위 프로젝트 브랜치를 **루트 저장소에서** 찾게 되어, 없으면 폴백으로 조용히 내려가 정리가 영영 일어나지 않고, 브랜치 이름이 겹치면 하네스 PR의 `MERGED`를 돌려줘 미머지 작업에 `branch -D`를 승인한다. cwd를 옮기지 않기로 한 결정(위)이 만든 부작용이며, 값을 `git -C project/<이름> remote get-url origin`에서 뽑게 해 해소했다. `gh pr create`도 같은 이유로 한정한다.

**`--no-track`이 필요한 이유(검증 F4).** `-b <브랜치> origin/main`은 새 브랜치의 upstream을 `origin/main`으로 잡는다(실측: `## chore/x...origin/main`). 그러면 worktree에서 `git status`가 "behind"라며 `git pull`을 권하고, 그 권유를 따르면 main이 피처 브랜치로 머지된다 — 이 스킬이 rebase로 지키려는 이력을 정확히 반대로 만든다.

**정리 판정을 `gh pr view` 1순위로 둔 이유는 실측 결과다.** 초안은 `git branch -r --contains`를 1순위로 적었으나, 실측(2026-07-29)에서 두 오판이 드러났다 — squash·rebase 머지는 커밋이 새로 쓰여 **머지된 브랜치가 미머지로 읽히고**(안 지우는 쪽이라 안전하지만, squash 머지 저장소는 이 경로로 영영 정리되지 않는다), 자기 커밋이 없는 브랜치는 tip이 곧 base라 **항상 머지로 읽힌다**. `gh pr view`는 PR 상태를 읽으므로 머지 방식과 무관하다. 폴백은 남기되 두 한계를 본문에 적었다.

**`worktree remove`의 거부가 데이터 손실 검사인 이유.** 미커밋·미추적 파일이 있으면 `--force` 없이는 exit 128로 거부한다(실측). 규칙이 판단하는 대신 git이 기계적으로 막으므로, "손실 없음"이 믿음이 아니라 명령 결과가 된다 — metaskill 공통 규칙 11~13이 택한 설계 방향과 같다. 그럼에도 §3 확인을 남긴 것은 하위 규칙이 §3을 완화할 수 없기 때문이며(§2), 확인은 배치 1회라 절차 비용이 라운드로 늘지 않는다.

**정본을 `branch-workflow`에 둔 이유.** `wrapup`은 스스로를 "얇은 오케스트레이터 — 저장·적용 로직을 재구현하지 않는다"로 규정한다. 브랜치의 생애주기를 쥔 쪽이 `branch-workflow`이므로 판정 규칙이 거기 살고, `wrapup`은 세션 전체 스윕 시점에 호출만 한다. 두 곳에 조건을 적으면 사본이 원본과 어긋난다.

## 영향

- `.agents/skills/branch-workflow/SKILL.md` — 시작 절차 재작성(worktree 생성·발동 조건·cwd 유지·`--no-track`·서브에이전트 경로 전달), 낡은 체크아웃의 진단 전 `fetch` 규칙, 마무리 절차의 worktree 경로 실행 명시와 `gh --repo`, 「Worktree cleanup」 절 신설(정본), 엣지 케이스 5종
- `.agents/skills/orchestrate/SKILL.md` — 7요소 CONTEXT에 「작업 위치」 추가, B모드 발행 프롬프트에 worktree 경로 명시 조항
- `AGENTS.md` §5·`AGENTS.ko.md` — 하위 프로젝트 브랜치 규칙을 worktree 기준으로 갱신(상시 로드 파일이 삭제된 절차를 서술하고 있었다 — 검증 F3)
- `.agents/skills/wrapup/SKILL.md` — 1단계 수집에 worktree 경로 상태 확인 추가(열거는 `worktree list`로 — 슬래시 브랜치는 중첩돼 glob이 중간 디렉토리를 내놓는다), 5단계 worktree 스윕 신설(위임), 기존 5단계 → 6단계
- `.agents/skills/carryover/SKILL.md` — 노트 템플릿 `Worktree` 필드, 재개 시 그 경로 사용 규칙, wrapup 단계 번호 참조 갱신
- `.agents/skills/work-tracker/SKILL.md` — wrapup 단계 번호 참조 갱신
- `.agents/skills/README.ko.md` — branch-workflow·wrapup·carryover 절 갱신
- `docs/README.md` — MOC 행 추가
- `project/.worktrees/` — 신설 디렉토리 규약(gitignore 상속, 파일 커밋 없음)

## 대안과 기각 사유

- **세션 cwd를 worktree로 이동(`EnterWorktree`)** — 크로스 프로젝트 작업이 갇히고 서브에이전트까지 상속된다(위 사유). 기각.
- **worktree를 `_workspace/worktrees/`에 배치** — 주간 하우스키핑 14일 삭제 후보 목록에 오른다. 기각.
- **worktree를 서브프로젝트 저장소 안(`project/<이름>/.worktrees/`)에 배치** — 그 저장소의 gitignore를 우리가 고쳐야 하고, ADR 006이 금지한 "남의 저장소에 우리 규약을 넣는" 형태가 된다. 기각.
- **읽기 작업까지 전부 worktree** — 생성·정리 비용만 들고 얻는 게 없다. 사용자 선택(2026-07-29)으로도 배제. 기각.
- **정리를 세션 종료 시 무조건 제거** — 미커밋 작업 손실. 사용자 선택으로 배제. 기각.
