# ADR 039 — 다이어그램 의무의 발동 조건과 `diagram` 스킬 포팅

- **날짜**: 2026-08-03
- **상태**: 활성 (**단계 번호 주의**: 아래 본문의 「branch-workflow 마무리 5」는 작성 시점 번호다. [ADR 041](041-comprehension-quiz-removal.md)이 마무리 4단계(이해도 퀴즈)를 삭제해 **PR 생성이 마무리 4로 당겨졌다** — 붙잡는 단계는 그대로 PR 생성 단계이며, 현재 번호는 `docs/README.md` 인덱스와 `branch-workflow` 본문을 따른다.)
- **관련**: AGENTS.md 13절(SDD·문서), ADR 017(ponytail 포팅 선례), ADR 030(영어 우선·한글 뷰), ADR 034(study 하네스 연계), `diagram` 스킬, `doc-writer`·`work-tracker`

## 변경 내용

1. **문서가 다이어그램을 빚는 조건을 내용에 대한 판정으로 정한다.** 넷 중 하나라도 **임계값을 넘으면** Mermaid 다이어그램이 **필수**다 — ⓐ 행위자 2인 이상 + 메시지 3개 이상, 그중 하나는 직전의 단순 응답이 아님(→ `sequenceDiagram`) ⓑ 상태 3개 이상 + '다음'이 아닌 전이 하나 이상(→ `stateDiagram-v2`) ⓒ 결정 2개 이상 또는 각 갈래가 2단계 이상 이어지는 결정 하나(→ `flowchart`) ⓓ 구성요소 4개 이상 + 관계 3개 이상이며 단일 선형 사슬이 아님(→ `flowchart`/`erDiagram`). 사슬은 N개면 관계가 항상 N−1개라 개수로 걸러지지 않는다. **임계값이 곧 규칙이다** — 맨 형태(행위자·상태·분기·구성요소가 있다는 것)는 어느 기술 문서에나 있다.
2. **어느 임계값도 못 넘으면 넣지 않는다.** 본문에 이미 있는 목록을 다시 그리는 다이어그램은 금지에 가깝다 — 리뷰 주의력을 쓰고 아무것도 더하지 않는다.
3. **발동 지점은 문서 유형 셋이다**(제목 셋이 아니다): 스펙의 **경계·설계를 서술하는 절**(템플릿에서는 `## 인터페이스 / 설계 개요`이지만 루트 하네스 스펙은 자체 번호 구조를 써서 22개 중 6개에 그 제목이 아예 없다 — 역할로 키를 잡는다), PR 본문의 `## 변경 내용`, work-tracker 이슈 템플릿에 신설한 `## 흐름`. README·런북·ADR·작업 리포트에서는 **권고**이며 아무것도 요구하지 않는다.
4. **`nohdol-study` 하네스의 `diagram` 스킬을 루트로 포팅한다** — SKILL.md(렌더 대상에 맞게 재작성)와 `scripts/check.py`·`check_test.py`(사실상 그대로).
5. **doc-writer 자체 검증 단계가 체커를 돌린다.** 다이어그램이 든 문서는 `check.py` 통과가 완료 조건이며, PR·이슈 본문처럼 파일이 없는 경우 scratchpad에 초안을 써서 검사한다.

## 대상

`.agents/skills/diagram/SKILL.md`(신설), `.agents/skills/diagram/scripts/check.py`(신설), `.agents/skills/diagram/scripts/check_test.py`(신설), `.agents/skills/doc-writer/SKILL.md`, `.agents/skills/doc-writer/references/templates.md`, `.agents/skills/work-tracker/SKILL.md`, `.agents/skills/team-review/SKILL.md`, `.agents/skills/branch-workflow/SKILL.md`, `.agents/agents/reviewer.md`, `.agents/agents/architect.md`, `.agents/skills/README.ko.md`, `CLAUDE.md`, `README.md`, `docs/README.md`, `docs/harness-changelog.md`, `docs/specs/2026-08-03-review-gate-hook.md`(ADR 039 첫 적용 — 시퀀스 다이어그램 추가)

## 사유

**사용자 보고(2026-08-03)**: "work-tracker 할 때 시퀀스 다이어그램이 없어서 불편한 적이 있다. 문서 작성할 때 이해를 높일 수 있으면 적극 활용하면 좋겠다."

산문이 못 하는 것이 둘이다 — **순서**와 **분기**. 읽는 사람이 그것을 머릿속에 세워야 하고, 다시 읽을 때마다 처음부터 다시 세운다. 세션이 바뀌어 맥락 없이 도착하는 work-tracker 이슈에서 그 비용이 가장 크다.

**그런데 "도움이 되면 쓰라"는 규칙은 적용되지 않는다.** 발동 조건이 없는 조항은 오늘 더 빠른 쪽에 진다 — 이 하네스가 여러 번 기록한 실패 형태이고(공통 규칙 15가 그것 때문에 있다), 그래서 판단을 **문서 내용에 대한 테스트**로 바꿨다. 같은 이유로 "넣지 않는다" 쪽도 함께 규정했다: 필수 조건만 있고 상한이 없으면 장식용 다이어그램이 늘어난다.

**포팅을 택한 이유**: `nohdol-study` 하네스에 이미 성숙한 `diagram` 스킬이 있다(도구 선택표, 라벨 함정 2종의 구분, 545줄 체커와 444줄 테스트). 런타임 참조(`vault-write` 방식)는 **사내 기계에 study 하네스가 없어** 통째로 안 되고, 새로 만드는 것은 이미 있는 실측 지식을 버리는 것이다. 사본이 둘이 되는 비용은 감수한다 — 렌더 대상이 다르므로(Obsidian vs 저장소 Markdown·이슈·PR) 두 사본은 **의도적으로** 갈라진다.

## 이 ADR이 2회 BLOCK 뒤에 다시 쓰인 기록

metaskill 개선 모드는 **한 작업 세션에서 같은 변경에 독립 리뷰 BLOCK이 2회 이상 나오면 그 자체를 신호로** 규정한다 — diff가 아니라 설계가 덜 정해진 채 들어갔다는 뜻이므로, 라운드별 수정을 멈추고 남은 범위를 스펙이나 ADR로 선정리하라는 것이다. 규칙 축에서 **세 라운드 연속 BLOCK**이 났다.

**원인은 하나가 아니라 둘이고, 둘째가 진짜다.**

**하나 — 설계 결함(1회, 재발 없음).** 초안의 발동 조건에 임계값이 없어 관할 절 16/16에 걸렸고 상한이 닿을 수 없었다. 조건마다 임계값 + 선형 사슬 배제 + 결정 기준의 operative화로 고쳤고, 이후 라운드에서 다시 나오지 않았다.

**둘 — 올바른 수정이 재진술 지점 일부에만 닿는 것(4회, 매 라운드 재발).** 1라운드 F1(단일 원본이 옛 절을 가리킴), 2라운드 D1(한글 뷰 2항목이 재키잉 전 문구를 그대로 보유), 3라운드 E1(유형별 붙잡는 단계 모델이 세 지점에 미도달), 4라운드 G1(문서 지도 인덱스 행이 폐기된 단일 홀더 모델을 그대로 보유). **매번 다른 표면으로 빠져나갔다** — 영어 원본 → 한글 뷰 → 계약 문서 자신 → 문서 지도. 셋째가 특히 나쁘고 넷째가 특히 얄궂다: ADR의 결정 표가 같은 ADR이 방금 만든 모델과 모순됐고, 그다음엔 **그 축을 닫으려던 라운드에서** 그 ADR을 열기 *전에* 읽는 인덱스 행이 폐기 모델을 먼저 건넸다. 넷째는 독립 검증이 문자열이 아니라 **읽어서** 찾았다 — 이 진단이 맞다는 증거다.

**이것이 이 절이 기록해야 할 교훈이다.** metaskill 공통 규칙 12(구성 지점 전수 열거)와 메모리 `term-revision-sweep-all-sites`가 이미 이 축을 겨냥하고 있는데도 세 번 다 못 막았다. 못 막은 이유는 규칙이 **용어 폐기**를 발동 지점으로 잡는데 여기서 바뀐 것은 용어가 아니라 **모델**(누가 무엇을 붙잡는가)이었기 때문이다. 용어는 `grep`으로 스윕되지만 모델은 안 된다 — 각 지점이 그 모델을 **재진술한 문장**을 읽어야 걸린다. 그래서 이 변경의 최종 스윕은 문자열이 아니라 "붙잡는 단계를 서술하는 문장"을 기준으로 돌렸다.

**남은 것도 같은 방식으로 판정한다** — 임계값은 확정값이 아니라 실측으로 한 번 교정된 값이다. 조정하려면 같은 코퍼스에 다시 돌려 발동/미발동이 어떻게 갈리는지를 근거로 댄다.

## 한계

- **GitHub 웹 UI가 Mermaid를 그림으로 렌더링하는지는 여기서 검증하지 못했다.** `POST /markdown`이 `highlight-source-mermaid`로 인식하는 것까지가 실측이고, 그 측정이 답한 질문은 "언어로 인식하는가"이지 "그림을 그리는가"가 아니다. 렌더링은 이슈·PR을 읽는 사용자가 확인할 축이다.
- **라벨 렌더 규칙은 Obsidian 번들 Mermaid 대고 실측된 것**이고 GitHub 버전은 미실측이다. 다만 규칙(따옴표·`<br/>`·목록 마커 회피)은 느슨한 렌더러에서도 비용이 0이라 그대로 따른다.
- **체커는 렌더러가 아니다.** Mermaid 파서는 JavaScript이고 이 저장소는 스크립트를 의존성 없이 유지하므로, 통과한 파일도 렌더에 실패할 수 있다.
- **사본 2개가 갈라진다.** study 쪽 원본과 루트 사본은 자동 동기화되지 않는다. 렌더 대상이 다르므로 대부분의 분기는 정당하지만, Mermaid 자체에 대한 새 실측이 한쪽에만 반영될 수 있다.
- **발동 조건의 판정 주체가 문서를 쓰는 세션 자신이다.** 체커는 다이어그램이 **있을 때** 그것을 검사할 뿐, **있어야 하는데 없는** 상태는 잡지 못한다. 그 축은 유형별 단계가 본다(양방향 — 누락과 과잉 둘 다): 스펙은 `team-review`·`reviewer`·`architect`, PR 본문은 `branch-workflow` 마무리 5, 이슈는 `work-tracker` 등록. **리뷰가 닿는 것은 스펙뿐**이라 나머지 둘은 작성 지점에서 잡을 수밖에 없다.
- **임계값 자체가 실측으로 교정된 값이다.** 임계값 없는 초안은 이 저장소의 관할 절 **16/16**에 발동했고, 그중에는 내용 전체가 `exit 0(통과) / exit 65(차단)`인 절도 있었다. 재키잉 후 표본 재판정에서 tdd-gate·secret-gate·tier-gate·token-efficiency 넷은 미발동, review-gate·autoloop 둘은 발동으로 갈렸다. 임계값이 더 조정될 수 있으며, 그 판단의 근거는 같은 방식의 재측정이다.
- **체커에 오탐 2종이 있었고 고쳤다**(퍼센트 인코딩 경로, 선행 `/` 경로). 게이트에서 오탐은 가장 비싼 방향이다 — 한 번의 헛된 "파일 없음"이 체커를 건너뛰게 만든다. 그래서 판정 불가한 대상은 전부 통과로 처리하며, 무엇이 검사되지 않는지는 스킬 6절에 열거했다.
