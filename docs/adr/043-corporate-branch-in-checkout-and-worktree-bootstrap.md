# ADR 043 — 사내 프로필의 worktree 폐기와 worktree 의존성 부트스트랩

- 날짜: 2026-08-05
- 상태: 활성
- 관련: ADR 035(하위 프로젝트 worktree 워크플로 — **사내 분기에 한해 이 ADR이 대체**), ADR 042(사내 프로필 발행 전면 차단), ADR 002(저장소 분리)

## 배경

ADR 035가 하위 프로젝트 작업을 `project/.worktrees/<이름>/<브랜치>/`의 worktree에서 하도록 바꿨다. 두 실패를 **구조로** 막는 것이 근거였다 — ① 낡은 브랜치에서 시작해 머지 시점에 충돌이 예약되는 것 ② 재개 세션이 조용히 `main`에 올라앉는 것. worktree는 브랜치를 하나만 쥐므로 ②는 표현 자체가 불가능해진다.

운영에서 두 가지가 관측됐다.

**사내 설치처에서 커밋·푸시·PR 단계가 깨진다**(사용자 보고, 2026-08-05). worktree 생성은 되지만 그 안에서의 커밋·푸시·PR이 실패하고, 같은 조작이 주 체크아웃에서는 성공한다. 이 저장소에서 원인을 특정할 수단은 없다 — 사내 git 서버·인증·프록시 설정은 이 기계에서 관측되지 않는다. 특정하지 못한 채로 결정한 이유는 아래 「대안」에 적는다.

**worktree는 의존성 디렉토리를 가져오지 않는다.** 저장소는 공유하지만 미추적 빌드 상태(`.venv`, `node_modules`)는 공유하지 않는다. 2026-08-05 실측: 등록된 6개 프로젝트가 전부 `.venv`를 갖고 있고(7~27MB), `telemetry-contract`의 것을 재생성하는 데 **8~12초**가 걸린다(2회 측정 — 실트리 8.1초, `git archive` 복사본 11.96초. 자릿수가 요점이고 초 단위가 아니다). 같은 날 `telemetry-contract` #3 작업에서 implementer가 worktree에 러너가 없는 것을 **작업 중에 발견**하고 스스로 만들었다 — 절차에 없어서 매번 각자 발견하는 상태였다.

## 결정

**1. 사내 프로필에서는 worktree를 쓰지 않는다.** `project/<이름>/` 체크아웃 하나에서 브랜치를 전환한다(ADR 035 이전 방식). 브랜치 이름 규약, 마무리 순서(검증 → rebase → push → PR), 머지 실측은 그대로다.

**ADR 035가 구조로 막던 두 실패는 절차로 되돌아오며, 그 사실을 스킬 본문에 명시한다.** 동등한 대체가 아니라 열등한 대체임을 적지 않으면, 사내 세션은 자기가 무엇을 잃었는지 모른 채 그 방식을 쓴다.

- 시작 전 `git -C project/<이름> status --porcelain`으로 미커밋 변경을 확인하고 사용자 판단을 받는다. `worktree add`는 그 체크아웃을 건드리지 않았지만 `checkout`은 작업 트리를 움직인다 — worktree 경로에는 없던 §3 데이터 손실 확인이다.
- 시작은 항상 갓 fetch한 `origin/main`에서 딴다(`checkout -b <브랜치> --no-track origin/main`).
- 재개 시 `symbolic-ref --short HEAD`로 현재 브랜치를 먼저 읽는다. worktree 도입 때 삭제된 재확인을 이 분기에서만 되살린다.

**2. 정리 절차에서 데이터 손실 가드가 사라지므로 명시적 검사로 보상한다.** 실측(git 2.39.5, 격리 저장소): 무관한 파일이 더티인 상태에서 `git checkout main`은 **성공하고 그 파일을 함께 데려간다**. 같은 상황에서 `git worktree remove`는 exit 128로 거부한다 — **그 거부가 곧 데이터 손실 검사였다**(ADR 035의 정리 조건 ②). 그래서 사내 분기의 정리는 `status --porcelain` → `checkout main` → `branch -d` 순서로 하고, 첫 단계에 무엇이든 있으면 정리를 멈춘다.

**3. worktree를 쓰는 경우(개인 프로필)에는 의존성 부트스트랩을 시작 절차에 명시한다.** worktree 생성 직후, 프로젝트 AGENTS.md가 기록한 명령으로 의존성을 설치하고, **테스트를 돌릴 발행 프롬프트에 그 단계를 적는다.**

**4. 의존성 디렉토리를 심볼릭 링크·복사로 공유하지 않는다.** 이 프로젝트들은 editable 설치(`pip install -e`)라 **빌린 환경이 어느 트리를 import하는지는 호출 방식에 달렸다** — 이 워크스페이스에서 실측돼 `.agents/projects/agent-eval-onboarding/AGENTS.md`에 기록돼 있다: `.venv/bin/python -m pytest tests/`는 *worktree의* 패키지를, `.venv/bin/pytest` 콘솔 스크립트는 *체크아웃의* 것을 집는다. 실패가 균일하지 않다는 것이 금지를 조건부가 아니라 전면으로 두는 이유다 — 위험한 쪽이 사람들이 실제로 타이핑하는 짧은 형태이고, 둘은 초록 결과만 봐서는 구분되지 않는다. 틀린 트리 위의 통과는 아끼는 10초 남짓보다 비싸다.

**5. 그 결과 `사내` 프로필에서는 하위 프로젝트 대상 무인 루프(`autoloop`)를 쓸 수 없다. 이것은 부작용이 아니라 유지되는 제약이다.** `driver.py`의 R18 가드는 대상이 연결된 worktree가 아니면 기동을 거부하는데(ADR 035), 이 결정이 그 사이트에서 worktree를 없애므로 거부가 항상 발동한다. **가드를 그대로 두는 쪽을 택한다** — R18이 막는 것은 "무인 세션이 사용자가 쓰는 체크아웃의 브랜치를 몇 시간 동안 움직이는 것"이고, worktree가 없는 사이트에서는 그 위험이 줄어드는 게 아니라 **격리 수단이 사라져 오히려 커진다**. `dispatch-gate`(ADR 042)는 `Agent`·`Task` 호출만 보므로 Bash로 뜨는 드라이버를 막지 않는다 — 즉 이 제약이 없으면 사내에서 무인 루프가 공유 체크아웃 위에서 돈다.

**남는 결함 하나는 후속이다**: R18의 거부 메시지가 `git worktree add`를 안내하는데, 사내에서는 이 ADR이 금지한 것을 하라는 말이 된다. 메시지 분기는 드라이버 코드 변경이라 `driver_test.py` 회귀와 독립 검증이 따로 필요하므로 이 변경에 넣지 않았다. 그때까지는 이 절이 그 안내를 정정하는 유일한 기록이다.

## 근거

개인 프로필에서 worktree를 유지하는 이유는 비용 비교다. 재설치는 작업당 1회 10초 남짓·27MB이고, ADR 035가 막는 실패는 머지 충돌과 잘못된 브랜치 작업이라 재작업 단위가 훨씬 크다. 사용자 상시 목표 3축 중 「무실수」가 「속도」에 앞선다는 기존 판단과도 같은 방향이다.

사내에서 폐기하는 이유는 **그 이점을 누릴 수 없기 때문이다.** worktree가 막아 주는 것은 머지 시점의 비용인데, 그 사이트에서는 커밋·푸시·PR 자체가 진행되지 않아 머지 시점에 도달하지 못한다. 도달하지 못하는 이점과 확실한 차단을 저울질할 것은 없다.

## 영향

- `AGENTS.md`·`AGENTS.ko.md` — 5절 하위 프로젝트 브랜치 규칙에 `사내` 한정 추가. **항상 로드되는 문서에 넣은 이유**: 사내 세션이 확실히 읽는 텍스트는 이것뿐이고, 스킬은 라우팅될 때만 로드돼 그 전까지 무조건형 규칙만 보인다(독립 검증 F1 — ADR 042도 프로필 분기를 루트에 반영한 선례). R14 예산(32,000) 때문에 3절에는 넣지 않고 5절 한 문장이 3절 예외의 무발동을 함께 지시한다
- `.agents/skills/branch-workflow/SKILL.md` — 사내 분기 절 신설, 시작 절차에 의존성 부트스트랩·공유 금지 문단 추가
- `.agents/skills/wrapup/SKILL.md` — 5단계에 사내 정리 분기(없으면 정리에 주인이 없다), 6단계 전제 문장 정정
- `.agents/skills/carryover/SKILL.md` — 노트 템플릿에 Branch 줄 신설, 재진입에 브랜치 선확인. **재개 세션은 `branch-workflow`가 아니라 이 스킬을 로드하므로**, 분기 3단계를 여기 다시 적지 않으면 그 보상이 도달하지 않는다(F5)
- `docs/adr/035-subproject-worktree-workflow.md` — 부분 대체 배너
- `docs/README.md` — MOC 043 행 추가, 035 행 상태 갱신
- `.agents/skills/README.ko.md` — branch-workflow 절 동조
- `docs/harness-changelog.md` — 이력 행

`orchestrate`의 `isolation: worktree`(병렬 쓰기 격리)와 agent-rules ⑨의 bisect 격리는 **대상이 아니다.** 둘 다 커밋도 푸시도 하지 않으므로 보고된 실패가 닿지 않고, 발행 1회 동안만 살아 의존성 문제도 다르게 걸린다. 사내에서는 ADR 042가 발행 자체를 막으므로 병렬 격리는 애초에 발동하지 않는다. **다만 그 차단에는 예외가 하나 있다** — `infra-specialist`는 사내에서도 발행되고 파일을 바꾸는 역할이므로(7절 5항), 그 발행이 하위 프로젝트를 대상으로 하면 `orchestrate`의 작업 위치 조항이 지시하는 worktree 절대경로가 사내에는 존재하지 않는다. 그 경우 체크아웃 경로와 브랜치를 대신 넘긴다(독립 검증 F9 — 좁지만 실재하는 잔여).

## 대안

**원인을 특정한 뒤 결정한다 — 기각.** 사내 git 서버·인증·프록시는 이 기계에서 관측할 수 없고, 사내 세션은 추적 파일을 편집할 수 없어(§5) 그쪽에서 이 스킬을 고칠 수도 없다. 원인 규명을 기다리는 동안 그 사이트는 작동하지 않는 절차를 계속 따르게 된다. **원인이 밝혀지면 이 결정은 되돌릴 수 있다** — 되돌리는 쪽이 프로필 분기 하나를 지우는 일이라 비용이 낮다는 점이 지금 결정할 수 있는 근거다.

**개인 프로필도 함께 폐기 — 기각**(사용자 판정, 2026-08-05). 절차가 하나로 통일되고 재설치가 사라지지만, ADR 035의 두 실패와 정리 시 데이터 손실 가드 상실을 전 설치처가 떠안는다. 10초 남짓을 아끼려고 구조적 보호를 버리는 교환이다.

**의존성 디렉토리 공유로 재설치를 없앤다 — 기각.** 위 결정 4의 근거(editable 설치에서 어느 트리를 import하는지가 호출 방식에 달려 있고, 위험한 형태가 더 짧다).
