# 하네스 문서 의미 검색 파일럿 — 기각(사전 바 미달)

- **날짜**: 2026-08-01
- **결과**: 기각(파일럿 미달 — 사후 바 조정 없음)
- **분류**: 이미 설치된 로컬 임베딩 서버를 하네스 코퍼스에 겨누는 검토

## 1. 대상

사용자가 `nohdol-study` 하네스용으로 세운 **로컬 임베딩 서버**(ollama, `127.0.0.1:11434`)와 그쪽 `vault-search` 스킬(`~/nohdol-study/.agents/skills/vault-search/`, `SKILL.md` + `scripts/semantic.py` 391줄)을 하네스 문서 검색에 이식할지 검토했다. 질문은 **"`rg`가 0.033초에 전체를 훑는 코퍼스에서 임베딩이 재현율을 실제로 올리는가"** 하나였다 — 속도는 애초에 축이 아니다.

`semantic.py`는 경로 규약이 vault에 결합돼 있어(`vault/wiki` 강제, 인덱스를 `vault.parent/_workspace/`) `--root`·`--include`·`--model`·청크 상한을 파라미터화해 포팅했다. loopback 강제, 콘텐츠 해시 기반 증분 갱신, `query`가 먼저 따라잡는 구조는 원본 그대로 유지했다.

- 코퍼스: `docs/**/*.md` 70건 + `.agents/**/*.md` 34건 = **1,185,031 B**
- 모델 2종 비교: `nomic-embed-text`(768차원, ctx 2048, 274 MB) / `bge-m3`(1024차원, ctx 8192, 1.2 GB)
- 청크 상한은 모델 컨텍스트에 맞춰 각각 900자·3,600자

## 2. 사전에 고정한 바와 편향 통제

실행 **전에** 고정했고 결과를 본 뒤 조정하지 않았다.

| 축 | 바 |
|---|---|
| ① 재현율 이득 | `rg`가 top-5에 정답을 못 넣은 질의에서, 의미 검색이 top-5에 넣는 비율 ≥ 60% |
| ② 퇴행 없음 | `rg`가 찾아낸 질의에서 의미 검색 top-5 정답률 ≥ 80% |
| ③ 운영 비용 | 초기 빌드 ≤ 5분(300초), 1파일 편집 후 증분 catch-up ≤ 10초 |

편향 통제 3종: ⓐ 질의에 정답 문서의 제목·고유 문자열을 쓰지 않는다 ⓑ 정답은 질의 작성 시점에 확정하고 이후 수정하지 않는다 ⓒ `rg` 키워드는 정답 문서를 보지 않고 질의 본문에서 기계적으로 뽑는다.

**통제가 지켜진 것은 파일 시각으로 확인된다** — `queries.json` 00:34:53 고정 → `rg` 측정 00:51~00:52 → 의미 검색 00:54(nomic)·01:03(bge-m3) → 영어 진단 01:07. 질의 12건, 정답 수정 0건, 무효 처리 0건.

## 3. 실측 결과 — 어느 모델도 세 축을 다 통과하지 못했다

`rg` 기준선 자체는 12건 중 **4건**(Q3·Q7·Q9·Q12)을 맞혔고, 이것이 축 ①(n=8)과 축 ②(n=4)의 분모가 된다.

| 축 | 바 | `nomic-embed-text` | `bge-m3` |
|---|---|---|---|
| ① 재현율 이득 | ≥ 60% | **0/8 = 0.0%** 미달 | **5/8 = 62.5%** 통과 |
| ② 퇴행 없음 | ≥ 80% | **0/4 = 0.0%** 미달 | **4/4 = 100%** 통과 |
| ③ 초기 빌드 | ≤ 300초 | **327.23초** 미달 | **644.47초** 미달 |
| ③ 증분 catch-up | ≤ 10초 | 2.9초 통과 | 3.0초 통과 |

`bge-m3`는 청크가 **40% 적은데도**(883개 vs 1,431개) 빌드가 **1.97배** 걸린다 — 8,192 컨텍스트에 맞춘 큰 청크가 1.2 GB 모델의 토큰당 비용을 되사지 못한다. 인덱스 크기는 nomic 4.9 MB, bge-m3 3.9 MB.

## 4. 모델 가설은 방향이 맞았고 이유가 달랐다

착안은 "코퍼스에 한글이 많으니 다국어 모델로"였다. **코퍼스 언어 가설은 반증됐다** — `nomic`은 한국어 `docs/`와 영어 `.agents/` **양쪽 다 0점**이다(0/7, 0/5). 한국어 문서에 약한 게 아니라 그냥 작동하지 않았다.

사전 등록한 영어 질의 진단이 진짜 축을 짚었다: **`nomic`은 한국어 질의에서 0/12, 영어 질의에서 2/3.** 축은 코퍼스가 아니라 **질의** 언어다.

붕괴의 성격도 근접 실패가 아니다:

```
nomic   : 12개 질의의 rank-1 문서 = 3종,  top-5 점수 폭 0.711~0.774 (0.063)
bge-m3  : 12개 질의의 rank-1 문서 = 11종, top-5 점수 폭 0.463~0.664 (0.201)
```

서로 다른 12개 질문이 3개 문서로 수렴하고 점수 폭이 0.063이면 순위가 질의를 반영하지 못한다는 뜻이다(한 제안서가 무관한 두 질의에서 0.741·0.752로 1위를 했다). **하네스 세션의 질의는 §15상 항상 한국어이므로 `nomic`은 이 용도에 쓸 수 없다** — 이 판정은 바와 무관하게 확정적이다.

## 5. 바보다 실질적인 제약 — 반환 단위

`bge-m3`의 히트 9건 중 **실제로 답이 든 구절을 반환한 것은 4~5건**이다. Q12는 `harness-changelog.md`를 맞혔지만 반환된 청크는 `git remote rename` 대목이었고, Q11은 `implementer.md` 2절을 줬는데 답은 4절에 있었다. **파일을 지목할 뿐 어디를 볼지는 말해주지 않으며, 235 KB짜리 changelog에서는 그것이 일의 대부분이다.**

표본도 얇다 — 축 ②는 n=4라 네 건이 전부 맞아야 80%를 넘고, 축 ①은 반 질의 차이로 통과했으며, 영어 진단은 질의 3건이다.

## 6. 결정

**기각.** `bge-m3`가 ①②를 통과했으나 ③ 초기 빌드가 허용치의 2.15배다. 사후에 바를 낮추는 것은 파일럿 자체를 무의미하게 만들므로 하지 않았다(선례: `2026-07-18-graphify-review`, 사전 바 미달로 기각).

하네스 규칙·설치 절차·라우팅은 이 검토로 바뀌지 않는다. 검색은 `rg`와 `docs/README.md`(MOC)를 계속 쓴다. 특히 **완결성 게이트(공통 규칙 11·12·14)의 `grep`은 어떤 경우에도 의미 검색으로 대체하지 않는다** — 하네스가 "`grep`은 문자열 존재만 증명한다"고 규정해 놓은 판정을 근사 검색으로 바꾸면 게이트가 불건전해진다.

## 7. 재검토 조건

기각 사유가 **비용 한 축**이므로 조건도 거기 걸린다. ①과 ②를 **함께** 충족할 때 다시 연다.

1. **초기 빌드가 실제로 바 안에 들어올 때** — 더 빠른 하드웨어, 더 가벼운 다국어 모델, 또는 증분만으로 초기 구축이 되는 구조. 추정이 아니라 빌드 1회 실측이 근거여야 한다. (증분 3초는 이미 통과했으므로 문제는 최초 1회뿐이다.)
2. **반환이 구절 수준이 될 때** — §5의 4~5/9가 개선되지 않으면 통과해도 이득이 절반이다. `semantic.py`는 이미 청크 단위로 임베딩하므로 청크 위치를 출력에 노출하는 선에서 해결 가능하다.

재검토 시 **질의 세트를 30건 이상으로 늘려** §5의 표본 문제를 함께 해소한다. `nomic-embed-text`는 §4의 근거로 재검토 대상이 아니다.

바를 다시 세워 2차 파일럿을 여는 것은 **별도 결정**이며, 이번 결과의 재해석이 아니다.

## 8. 미검증 범위

- **`bge-m3`의 catch-up 초기 측정 19.4초·42.9초는 한 ollama 인스턴스에서 두 모델을 번갈아 쓴 인공물**이었고, 상주 상태 재측정 3.0초를 채택했다. 다섯 판독 모두 리포트에 인쇄돼 있으나 축 ③ 판정은 빌드 쪽에서 갈렸으므로 이 정정은 결론에 영향이 없다.
- **영어 질의 진단은 3건**이다. `nomic`의 한국어 붕괴가 코퍼스가 아니라 질의 축임을 세우는 데는 충분하나, 영어 질의 성능 자체의 추정치로 쓰기에는 표본이 부족하다.
- **사전 등록의 한계 1건**: Q7의 정답 집합이 `wrapup/SKILL.md`를 빠뜨렸는데 `bge-m3`가 그것을 1위로 반환했다. 통제 ⓑ에 따라 정답을 고치지 않고 기록만 남겼다.
- 첫 `rg` 실행이 top-5를 `.py` 파일에 낭비하고 gitignore된 코퍼스 파일을 건너뛴 결함이 있어, **의미 검색을 돌리기 전에** 고쳤다(`raw/rg_results_uncorrected.txt` 대 `rg_results.txt`). 수정 방향은 기준선을 **강화**하는 쪽이었다(Q7에서 `rg`가 정답 하나를 더 얻었다).
- 축 ③ 측정을 위해 색인된 파일 하나(`docs/adr/003-perfectionism-clause-removal.md`)를 편집했다가 바이트 동일하게 복원했다. sha256 왕복과 `git status` 공백을 각각 확인했다.
