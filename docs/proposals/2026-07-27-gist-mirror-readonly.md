# secret gist 미러 재도입 — 단방향 read-only형

> 2026-07-26에 도입했다 같은 날 철회한 하위 하네스 gist 미러를, **철회 사유였던 방향 통제를 기계로 해결한 형태**로 다시 제안한다. 대상은 `.agents/projects/<이름>/`의 개인 PC → 사내 이송 경로 하나뿐이다.

## 대상 요약

하위 하네스(`.agents/projects/<이름>/AGENTS.md` 등)는 미추적이라 어느 저장소에도 없고(ADR 005·006), 루트 하네스 저장소는 public이라 사내 규칙을 실을 수 없다. 현재 이송 수단은 **사용자의 손 복사** 하나다.

- **도입**: `100891f` (2026-07-26) — `gh gist create/edit/view` 3건 실측 후 배선
- **철회**: `e0f21b1` (같은 날) — 독립 검증 4·5·6라운드 연속 BLOCK
- **철회 사유(ADR 006 철회 행)**: gist가 개인 계정에 있어 **사내에서의 push가 곧 반출**인데(§3), git 경로의 `set-url --push … DISABLED` 같은 **기계적 차단이 없었다.** 방향을 규칙으로만 만들려 하자 변경 이력 행(신선도 대조 신호)과 충돌했고, 면제로 풀자 면제가 "모든 변경을 이력에 기록" 의무와 다시 충돌했다.

## 왜 다시 보는가

**기능은 실패한 적이 없다.** 배선 커밋에 `gist create`(`--secret` 플래그 없음, 기본 secret), `gist edit`(exit 0 후 내용 일치), `gist view --raw`(description·빈 줄을 앞에 붙여 `-f` 필수) 3건의 실측이 남아 있고, 사용자 보고로 **실제 반입에서 토큰을 언급하자 정상적으로 받아왔다**(2026-07-27). 철회는 도구가 아니라 **그 도구에 방향을 부여할 수단이 규칙뿐이었다**는 설계 결함 때문이었다.

그 결함에 이번에 답이 생겼다.

## 설계 — 사내 쪽에 자격증명을 두지 않는다

| 축 | 개인 PC(내보내는 쪽) | 사내(받는 쪽) |
|---|---|---|
| 자격증명 | `gist` 스코프 토큰 보유 | **없음** |
| 가능한 동작 | 생성·갱신·조회 | **조회만** |
| 사용 명령 | `gh gist create/edit` | `curl <raw URL>` |

**기계적 근거 2건(1차 출처 확인)**

1. **읽기 전용 gist 토큰은 존재하지 않는다.** GitHub OAuth 스코프 표의 gist 항목은 `gist` 하나이며 설명이 *"Grants write access to gists."* 다. fine-grained PAT은 gist를 지원하지 않는다. → **토큰 스코프로는 방향을 못 만든다**(초기 가설 기각).
2. **secret gist는 인증 없이 URL만으로 읽힌다.** GitHub 문서: *"If you send the URL of a secret gist to a friend, they'll be able to see it. However, if someone you don't know discovers the URL, they'll also be able to see your gist."* 즉 secret은 **비공개가 아니라 미등재**다. → **사내는 토큰 없이 받을 수 있고, 토큰이 없으면 쓸 수 없다.**

이 조합이 철회 사유가 지목한 부재를 정확히 메운다. 오히려 `set-url --push … DISABLED`보다 강하다 — 그 장치는 누구나 되돌릴 수 있지만, 없는 자격증명은 새로 발급받아야 한다.

**규칙 연쇄 충돌도 함께 사라진다.** 철회를 부른 연쇄는 "사내 수정을 미러에 반영할 의무 ↔ 방향 규칙 ↔ 변경 이력"이었는데, 사내가 구조적으로 쓸 수 없으면 **그 의무 자체가 생기지 않는다.** 그 자리는 이미 있는 규칙이 덮는다 — metaskill 반입 시나리오의 *"A step-4 edit made inside stays inside until the user carries it… say plainly that the outside copy is now behind."*

## 채택 범위·경계

- **범위**: 개인 → 사내 방향, 하위 하네스 문서 이송 한 건. 반대 방향(사내 → 개인)은 **손 이송 유지** — 자동 채널을 두면 반출 경로가 된다는 철회 판단은 그 방향에 대해 여전히 유효하다.
- **기각**: 사내 쪽 토큰 발급(2번 근거로 불필요하고, 발급하는 순간 방향 통제가 규칙으로 되돌아간다). 프로젝트 저장소에 하네스 파일 싣기(ADR 006 — 남의 저장소일 수 있다).
- **레지스트리**: gist ID는 REGISTRY.md(미추적)에 기록한다. 이 항목 자체가 §3 반출 주의 대상이다.

## §3 유출 처리

**남는 위험은 하나다 — URL을 아는 누구나 읽는다.** secret은 검색·목록에 안 뜰 뿐 접근 통제가 아니다.

- 미러에 올리는 것은 **개인 PC가 만든 하위 하네스 문서뿐**이며, 이미 §3 반출 주의(고유값 금지 — 호스트명·클러스터·조직명 등)를 받는 텍스트다. 사내가 쓸 수 없으므로 **사내 내용이 이 채널로 들어갈 경로가 없다**.
- 판정 단위는 파일 전체다. `gh gist edit` 실행 시점이 §3 발동 지점이며, 이는 이미 REGISTRY.md 「반출 주의」에 기록돼 있었다(`e0f21b1`에서 철회되며 빠졌으므로 되살린다).
- URL 유출 = 내용 유출. 따라서 gist ID는 미추적 파일에만 두고 커밋·PR·이슈에 싣지 않는다.

## 재검토 조건

- GitHub가 읽기 전용 gist 스코프를 제공하면 사내 쪽 조회를 인증 경로로 바꿀 수 있다(현재는 불가).
- 사내에서 미러에 쓸 필요가 실제로 관측되면 **이 설계는 성립하지 않는다** — 그때는 재도입이 아니라 철회 결정으로 되돌아간다.
- 손 이송으로 충분하다고 판명되면(2026-07-27 신설한 "부재를 추론하지 말고 물어라" 규칙이 조용한 실패를 이미 막는다) 이 미러는 신호 ④의 폐기 대상이다.
