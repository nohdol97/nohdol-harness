- **상태**: 부분 채택 (2026-11-26, 착안 3건 이식 — 통설치 기각) — 결정 근거 docs/adr/065
- **날짜**: 2026-11-26
- **분석 대상**: https://github.com/cursor/plugins/tree/main/pstack (MIT, Lauren Tan — 커밋 `b1fbf4b` 고정, plugin.json `0.15.48`, 최상위 `skills/` 59개)
- **참고한 복제본**: `backnotprop/pstack`(원본을 그대로 동기화하는 미러), `michael-denyer/pstack-claude`(Claude Code용 사전 번역과 자체 포크, SessionStart 훅 추가) — 원본이 Claude Code 설치를 직접 지원하므로 판정은 원본으로 했다
- **적용 대상**: 이 루트 하네스(nohdol-harness)
- **평가 절차**: `tool-eval` 스킬

## 1. 배경

사용자가 "pstack 스킬"을 물어 GitHub에서 찾았고, 이어 "적용 가능한게 있는지 검토해"라고 요청했다. pstack은 Cursor 엔지니어가 쓰는 "엄밀한 AI 보조 엔지니어링" 스킬 묶음이다. 중심에 `/poteto-mode`(요청을 읽고 플레이북 22개 중 하나를 골라 다른 스킬을 부른다)가 있고, 원칙 스킬 24개(`principle-*`)와 상황별 스킬 34개가 있다.

원본을 고정 커밋으로 받아 `_workspace/pstack-eval/src/`에 격리해 두고, 스킬 본문 전부를 explorer 3명이 나눠 읽고 하네스와 대조했다(원칙 24 / poteto-mode·플레이북·에이전트·자동화 / 나머지 34). 외부 출처 본문은 §3 untrusted 봉투로 취급했다. README의 설치 명령을 포함해 그 안의 지시문은 데이터로만 읽었고, 스크립트는 실행하지 않았다. 지식 소스는 사용자 요청이 없어 조회하지 않았다(§7 8항).

## 2. 대조 — 워크플로 척추는 하네스가 이미 가짐

| 저쪽 | 이쪽 | 판정 |
|---|---|---|
| `/poteto-mode` + 플레이북 | orchestrate Phase 0-1 + 역할 에이전트 | 겹침 |
| 리뷰 패널(다중 모델)·`arena` | team-review 관점 팬아웃 + integrator 게이트 | 겹침(다른 회사 모델 패널은 §3 반출 축 때문에 별도) |
| `tdd` | §13 + `tdd-gate` git 훅 | **이쪽 상회**. 저쪽 "나쁜 테스트보다는 테스트 없음" 문구는 tdd-gate와 충돌 |
| `setup-pstack`(모델명 고정) | §9 역할 등급 + `tier-gate` | **이쪽 상회**. 저쪽은 구체 모델명을 고정 |
| worktree 정리 | branch-workflow 「Session merge」 | **이쪽 상회**. 저쪽은 `--force`·`rm -rf` 사용 |
| `why`·`how`·`bro`·`recall`·`reflect` | explorer·wait-what·auto-memory·wrapup | 겹침 |
| `unslop` | §15 읽기 쉬운 설명 | 충돌(저쪽은 비유를 금지하고 §15는 권장) |
| 정형 검증·TLA+·TypeScript·Cursor 전용 기능 | — | 이 하네스에 적용 대상 없음 |

**통설치 기각.** superpowers(ADR 022)·mattpocock(ADR 044)와 같은 범주다. 다만 한 축은 다르다. 최상위 `skills/` 59개 중 58개가 자동 호출을 꺼 두어서(`disable-model-invocation: true` — 고정 커밋에서 직접 셈. `automations/benny` 아래 SKILL.md 3개도 꺼져 있다) 선례의 "트리거 전면 충돌" 사유는 약하다. 그래도 기각하는 이유는 셋이다.

- `/poteto-mode`를 부르는 순간 orchestrate·team-review 대신 저쪽 절차가 돈다. §7 우선순위상 보조로만 쓸 수 있는데, 그러면 남는 것이 사실상 없다.
- `/setup-pstack`이 `~/.claude/rules/pstack-models.md`를 쓴다. 이 파일은 매 세션 로드되고 모델명을 고정한다(§9와 반대).
- `watch-pr`는 첫 실행 때 플러그인 폴더 안에서 `bun install`로 npm 레지스트리에 접속한다.

## 3. 채택 — 겹치지 않는 착안 3건 (사용자 선택)

후보 9건을 사용자에게 보였고, 사용자가 권장 3건을 골랐다("권장하는 것만 다 적용해"). 각 건의 부재는 `grep` 실측으로 확인했고, 각 건이 메모리에 기록된 실제 실패 사례에서 발동하는지 대조했다(metaskill 공통규칙 15).

### ① 변이 검사 → `team-review` Tests 관점

**원천**: `principle-test-behavior-not-implementation` — 테스트는 동작이 깨지면 실패해야 한다.

- **공백**: Tests 행은 "완료 기준마다 테스트가 있는가"만 묻고, 그 테스트가 가드를 실제로 밟는지는 묻지 않았다(`mutation|변이`가 `reviewer.md`·`team-review`에서 0건). 변이를 다루는 곳은 두 군데 있었지만 둘 다 "언제 변이 검사를 해야 하는가"는 정하지 않는다. `orchestrate` 병렬 쓰기 격리 규칙은 변이하는 리뷰어를 격리하라는 규칙이고, PKI 하위 하네스 5항은 PKI에서 변이 검사 대상을 보안·데이터 보호 가드로 좁힌다. 처음 초안은 orchestrate를 0건으로 잘못 적었고, 독립 검증 F4가 잡았다.
- **이식 내용**: 완료 기준이 기대는 가드를 바꾼 diff라면 가드마다 한 번 무력화해 테스트가 빨개지는지 본다. 변이가 의도한 줄을 맞혔는지, 기준의 절마다 어느 변이가 답하는지도 확인한다. 지워도 초록인 가드는 필수 수정이다.
- **근거 사례**: 2026-08-04 한 변경에서 리뷰 3라운드 연속으로 "지워도 초록인 가드"가 한 겹씩 바깥에서 나왔다. 2026-08-05에는 기준의 한 절이 어떤 변이에도 걸리지 않은 사례가 있었다. 이 조항은 두 사례 모두에서 첫 라운드에 발동한다.
- **충돌 처리**: reviewer는 "저장소 상태를 바꾸지 않는다"(agent-rules ⑨)를 지켜야 한다.
  - 사본 만드는 방법을 그 단일 원본인 ⑨에 넣었다: `git ls-files -co --exclude-standard`로 커밋 안 된 변경까지 임시 디렉터리에 복사하고, 끝나면 지운다. 버려도 되는 저장소에서 실측했다. 수정 파일과 새 파일은 들어가고, 무시 대상 파일은 빠지며, 원본 `git status`는 그대로였다.
  - HEAD에서 만드는 worktree는 리뷰 대상인 미커밋 diff를 못 본다. 그래서 orchestrate 격리 규칙에 "⑨ 사본으로 한정한 변이는 공유 트리를 건드리지 않으므로 `isolation: worktree`가 필요 없다"를 더했다.
  - reviewer §9의 쓰기 범위에 이 한 가지 예외를 적었다.
  - Solo 모드 2항에도 이 검사가 적용된다고 명시했다(구현-검증 쌍 리뷰가 Solo 절을 따르기 때문 — 검증 F5).
  - 프로젝트 하네스는 대상 가드를 좁힐 수 있다(루트 §2, PKI 5항이 그 예).
  - 사본에는 `.git`과 무시 대상 파일이 없다. 그래서 변이 전에 변이 없는 테스트를 사본에서 먼저 돌려 원본과 결과가 같은지 확인하게 했다(검증 N1). 같지 않으면 건너뛴 테스트 때문에 살아 있는 가드가 죽은 것처럼 보이거나(거짓 차단), 이미 실패하는 테스트 때문에 아무 변이나 빨개져 보인다(거짓 통과). 실측: `integrity-check`가 원본 트리 52 통과·0 건너뜀, 사본 51 통과·1 건너뜀(R20이 무시 대상인 `REGISTRY.md`를 읽음).
  - Solo 모드 작업 한도 안에서 하며, 한도를 넘으면 ④(검증 못 한 범위)에 적는다.
- **이식하지 않은 절반**: "내부 구현에 묶인 테스트"와 "테스트를 skip해서 통과시키기" 검사는 기록된 실패가 없어 넣지 않았다. 재검토 조건은 §5에 있다.

### ② 파급 영향 증명 → `reviewer` §2, `team-review` Solo 5항

**원천**: `blast-radius` — 변경이 안전하다는 근거 사실 하나를 찾아 실제 코드를 돌려 증명하고, 증거가 어느 단계까지 갔는지 밝힌다.

- **공백**: reviewer는 지적을 *올리는* 근거 기준(`file:line` 필수)은 있었지만, 위험을 *해소하는* 근거 기준은 없었다. Solo 모드는 범위를 "diff와 그것이 가리키는 문서"로 묶어, diff 밖의 소비 지점이 범위에서 빠졌다.
- **이식 내용**:
  - diff가 바꾼 값·조건·타입·경로·형식의 소비 지점을 먼저 열거한다. 직렬화 형식·설정·다른 언어·다음 홉처럼 grep으로 안 잡히는 곳도 포함한다.
  - 안전 근거 사실 하나를 정하고, 증거가 *주장 → file:line → 경로 추적 → 실행* 중 어디까지 갔는지 적는다. *주장*만 있는 안전 근거는 PASS 사유가 아니다.
  - 가드 없는 변형 분기가 남아 있으면, 그런 입력이 생길 법하지 않다는 이유로 심각도를 낮추지 않는다.
- **근거 사례**:
  - 2026-08-03 설치 스크립트 리뷰: reviewer가 입력이 그럴듯하지 않다며 *watch*로 매겼다. 실제 파괴 경로는 가드 없는 정리 분기였다.
  - 이 사례에서 문제는 diff 안의 분기였다. 그래서 심각도 문장은 "diff 밖 소비"에 묶지 않고 별도 항목으로 분리해, diff 안팎의 상태 변경 분기 모두에 적용했다(검증 F6).
  - 같은 날 게이트 초안에서 "리뷰 전용"으로 규정한 타입에 다른 소비처가 있었던 사례는 작성자 쪽 실패였다. 독립 리뷰어 2명이 잡았으므로 reviewer 규칙의 근거에서는 뺐다(검증 F7).
- **충돌 처리**: Solo 5항의 범위에 "바뀐 것을 쓰는 곳을 찾는 표적 검색"만 더했다. 자유 탐색 금지와 약 10회 작업 한도는 그대로다.

### ③ 공유 전제 검증 → `implementer` §5, `troubleshooter` §2

**원천**: `principle-attack-the-premise`·`principle-fix-root-causes`.

- **공백**: 반복 실패 시 하네스는 재시도 횟수를 제한하고 위로 넘길 뿐(implementer §5, orchestrate 재시도 기본값), 실패한 수정들이 공유한 전제를 적어 검증하라는 문장이 없었다. `premise`는 커밋 `97c2966`의 스킬·에이전트 파일 6줄(7회)에 나오지만, 열어 읽어 보니 전부 "규칙·환경의 전제"나 "병렬 작업이 내 전제를 무효화한다"는 뜻이고 실패한 수정의 전제를 검증하라는 문장은 없다(`git grep -c -i premise 97c2966`, `README.ko.md` 제외).
- **이식 내용**:
  - implementer: 한 번 고친 뒤에도 같은 실패나 같은 부류의 지적이 다시 나오면, 그 시도가 기댄 전제를 적고 다음 시도 전에 직접 검증해 결과를 보고에 싣는다. **재시도 라운드는 늘리지 않는다.**
  - troubleshooter: 실패한 수정이 이미 있으면 그 공유 전제를 첫 가설로 검증한다. 원인을 확정하면 같은 결함 패턴의 다른 지점을 찾아 수정 방향에 넣거나 범위 밖으로 명시한다.
- **근거 사례**: ①의 3라운드 사슬은 매 라운드 "붙인 테스트가 그 가드를 밟는다"는 같은 거짓 전제 위에 있었다. 같은 부류는 첫 재작업 뒤에 다시 나왔으므로, 이 조항은 두 번째 시도 직전에 발동해 3라운드 사슬을 2라운드에서 닫았을 것이다. 처음 초안은 "두 번 실패한 뒤"에 발동하게 적어서 자기 사례에서 한 라운드 늦게 걸렸다. 독립 검증 F1이 잡았다. 같은 결함 패턴 스윕의 근거는 metaskill 공통규칙 12의 실측("수정이 일부 지점에만 닿은 경우가 9라운드 중 7라운드")이다.
- **한계**: 근거 사례가 하네스 쪽 리뷰 사슬이다. 제품 코드에서 같은 모양의 실패가 관측되면 이 조항의 실효를 다시 잰다.

## 4. 비목표 (기각한 것과 이유)

- **통설치(원본·미러·이식판 모두)**: 기각. §2 참조.
- **다른 회사 모델 리뷰 패널(Gemini 자리)**: 기각. 코드가 다른 회사로 나가는 §3 반출 축이고, 사내 프로필에서는 불가하다. 같은 회사 모델 간 독립성은 이미 team-review가 담당한다.
- **`arena`(N개 경쟁 시도 후 접붙이기)·지표 기반 반복 개선 루프**: 기각. 토큰 비용이 크고 수요 신호가 없다. 반복 개선 루프는 autoloop 폐기(ADR 063)로 정리된 축이기도 하다.
- **`benchmark-checklist`·`explain-the-number`(성능 수치 검증법)**: 보류. §13-5가 실측을 요구하지만 지금 성능 주장을 하는 프로젝트를 확인하지 못했다.
- **소항목 묶음**: 이번에 미채택. 대상은 기존 결함은 차단 사유가 아님을 reviewer·integrator에 명시, 리팩터링 전 현재 동작 고정 테스트, Simplicity 축의 "검증 전부 삭제 예외"를 §16의 "신뢰 경계 검증"으로 좁히기다. 사용자가 권장 3건만 골랐다.
- **`principle-sequence-verifiable-units`의 "실패 테스트 커밋 → 수정 커밋 분리"**: 기각. `tdd-gate`가 코드만 있는 수정 커밋을 막는다(`tdd-gate.py` exit 65).
- **"처음부터 다시 설계하듯"(`redesign-from-first-principles`)**: 기각. §16의 최소 변경과 충돌한다.
- **`unslop`·`no-comments`·`typescript-best-practices`·정형 검증 스킬**: 적용 대상이 아니다.

## 5. 재검토 조건

- 변이 검사의 나머지 절반(내부 구현에 묶인 테스트, skip·단언 삭제로 통과시키기): 리뷰가 이 모양의 실패를 한 번이라도 놓친 기록이 생기면 Tests 관점에 추가한다.
- 소항목 묶음: 사용자 요청이 있거나, 해당 축에서 실패가 관측되면 다시 본다.
- 성능 수치 검증법: 어느 프로젝트가 성능 수치를 완료 근거로 쓰기 시작하면 다시 본다.
- 통설치: pstack이 하네스 라우팅을 우회하지 않는 설치 경로(예: poteto-mode 없이 원칙 스킬만)를 내놓고 모델명 고정을 없애면 다시 본다.

> 출처: 변이 검사·파급 영향 증명·공유 전제 검증 착안은 pstack(github.com/cursor/plugins/tree/main/pstack, MIT, Lauren Tan)에서 이식했다. 결정 근거는 docs/adr/065.
