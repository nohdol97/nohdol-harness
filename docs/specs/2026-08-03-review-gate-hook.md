# review-gate 훅 — 사내 프로필에서 검증 목적 발행 차단

> 상태: 구현됨 · 작성 2026-08-03 · 결정: ADR 038

## 1. 배경

검증 목적 서브에이전트 발행 1회의 실측 비용은 **약 100k 토큰과 수 분**이다(metaskill 개선 모드 「검증 비례성」 항이 인용하는 2026-07-17 세션 reviewer 6회 평균). 개인 설치처에서는 이 비용이 품질 대비 타당하지만, **사내 설치처에서는 감당되지 않는다**(사용자 판정 2026-08-03).

문제는 그 의무가 규칙 문서에만 적혀 있다는 점이다. `orchestrate`의 「검증 필수 규칙」은 "구현이 포함되면 독립 reviewer 검증을 생략할 수 없다"고 못박고, `team-review`는 Solo/Team 두 경로 모두 reviewer로 수렴한다. 즉 사내 세션이 규칙대로 움직이면 비용이 발생하고, 규칙을 어기면 그 사실이 어디에도 남지 않는다. **tier-gate와 같은 실패 형태다** — 발행 지점에 장치가 없으면 판정이 세션의 기억에 달린다.

## 2. 목표 / 비목표

**목표**

- 설치처 프로필이 `사내`일 때 **검증 목적 서브에이전트 발행을 발행 시점에 차단**한다.
- 차단 메시지가 **대체 절차**(메인 루프 자체 검증 + 면제 명시 기록)와 **우회 방법**(사용자 명시 요청)을 함께 알린다.
- 개인 설치처의 동작은 **한 바이트도 바뀌지 않는다**.

**비목표**

- 빌드 측 발행(implementer·explorer·troubleshooter·architect·infra-specialist 저작)은 대상이 아니다. 사용자가 지목한 비용은 검증 축이다.
- 리뷰 **품질**을 판정하지 않는다. 훅은 발행 여부만 본다.
- 테스트·스펙 게이트·§3 가드레일은 손대지 않는다. 이 변경이 없애는 것은 **검증자**이지 증거가 아니다.

## 3. 요구사항

| ID | 요구사항 |
|---|---|
| R1 | `tool_name`이 `Agent`/`Task`이고 `subagent_type`이 **검증 말고는 쓰이는 곳이 없는 역할일 때만** 판정한다 — 이 하네스에서 그런 타입은 `reviewer` 하나다(4절) |
| R2 | REGISTRY.md 「설치처 프로필」이 `사내`일 때만 차단한다. 그 외(`개인`·미상·부재·판독 실패)는 통과 |
| R3 | 발행 프롬프트에 `[review-ok]`가 있으면 통과한다 — 사용자 명시 요청의 표식(§8 선례, `[no-test]`·`[secret-ok]`와 같은 계열) |
| R4 | 차단 시 stderr로 대체 절차와 우회 방법을 알리고 exit 2 |
| R5 | 어떤 예외·형식 불명 입력도 통과(fail-open). **이 훅의 fail-open 방향은 "검증이 돌아간다"** — tier-gate와 반대로, 판독 실패가 안전한 쪽으로 떨어진다 |
| R6 | 프로필 판독은 `_common.read_profile` 단일 원본을 쓴다. 파서를 복제하지 않는다 |
| R7 | 등록 shim은 훅 파일 부재 시 통과한다(`[ -r "$f" ] \|\| exit 0`) — tier-gate가 독립 검증 F2에서 받은 지적과 같은 형태 |

## 4. 판정 범위의 한계 (명시)

**훅은 규칙보다 좁고, 그것이 설계다.** 규칙(ADR 038)이 끄는 것은 "검증 목적 발행"이라는 **의도**인데, 훅이 볼 수 있는 것은 `subagent_type`이라는 **타입**뿐이다. 두 축이 1:1인 타입은 `reviewer` 하나이므로 훅은 그 하나만 막는다.

**과잉 차단 축 — `integrator`와 `infra-specialist`는 넣지 않는다.** 둘 다 검증에도 쓰이지만 검증 아닌 용도가 각각 있다: `integrator`는 `project-status` 2절(상태 아티팩트 fan-in)과 orchestrate 표준 골조 ⑤에, `infra-specialist`는 매니페스트 저작에 쓰인다. 타입으로 막으면 사내에서 `project-status`가 통째로 죽고, **정당한 우회가 없다** — `[review-ok]`는 사용자가 리뷰를 요청했다는 표식이라 아무도 요청하지 않은 발행에 달면 그 표식의 유일한 값(요청의 기록)이 사라진다. 그래서 이 두 축은 **규칙만으로 관장**한다. 초안은 `integrator`를 넣고 있었고 **독립 검증 2인이 각각 같은 결함으로 지적했다**(2026-08-03).

**과소 차단 축 — 로스터 밖 타입은 통과한다.** `general-purpose`로 리뷰를 시키면 훅에 걸리지 않는다. tier-gate와 같은 구멍이고, 같은 이유로 감수한다 — 타입이 아니라 의도를 판정하려면 훅이 프롬프트를 해석해야 하고 그 판정은 신뢰할 수 없다.

**우회 표식은 게이트 대상이 쥐고, 매칭도 느슨하다.** `[review-ok]`를 프롬프트에 넣는 주체는 세션 자신이며, 문자열이 프롬프트 어디에 있든 통과한다 — 리뷰 발행은 diff를 인라인하는 것이 기본이라 **인용된 텍스트 안의 표식도 통과시킨다**. `[no-test]`·`[secret-ok]`가 이미 같은 구조이고, 실패 방향이 안전한 쪽(리뷰가 돌아간다)이라 수용한다. 기계적 보증이 아니라 **기록이 남는 우회**라는 점이 이 표식의 값이다.

## 5. 완료 기준

- [x] C1 (R1·R2·R4): 프로필 `사내` + `reviewer` 발행 → **리터럴 exit 2**(PreToolUse가 키로 삼는 값이므로 상수가 아니라 리터럴로 고정한다), stderr에 대체 절차·ADR 번호·우회 표식
- [x] C2 (R1): `tool_name`이 `Task`인 갈래도 같이 판정된다
- [x] C3 (R2): 프로필 `개인` + `reviewer` 발행 → exit 0, stderr 없음
- [x] C4 (R2): REGISTRY.md 부재 → exit 0 (미상은 차단하지 않는다)
- [x] C5 (R1): 프로필 `사내` + **`integrator`**·`implementer`·`explorer`·`infra-specialist`·`troubleshooter`·`architect`·`general-purpose` → exit 0 (4절 과잉 차단 축의 고정)
- [x] C6 (R3): 프로필 `사내` + `reviewer` + 프롬프트에 `[review-ok]` → exit 0
- [x] C7 (R1): `tool_name`이 Agent/Task가 아니면 exit 0
- [x] C8 (R5): 형식 불명 stdin(빈 문자열·비JSON·배열·`tool_input: null`) → exit 0, 무출력
- [x] C9 (R5): 판독 함수가 예외를 던져도 exit 0. `subagent_type`이 문자열이 아니어도 exit 0
- [x] C10 (R6): 훅이 쓰는 판독기가 `_common.read_profile` **그 객체**다(복제로 되돌아가는 회귀를 막는 위치 고정)
- [x] C11 (R6): `harness-review-reminder` 스위트 37건이 이관 후에도 전부 통과 — 프로필 절 한정·코드 펜스·제목 레벨의 의미 축은 **그 스위트가 같은 함수에 대고** 판정하므로 여기서 다시 세우지 않는다(§16)

> C1~C10은 `python3 .agents/hooks/review-gate_test.py`(11건), C11은 `python3 .agents/hooks/harness-review-reminder_test.py`(37건)로 판정한다. 스위트가 실제로 무언가를 고정하는지는 **변이 5종**(`BLOCK_EXIT`→0, `AGENT_TOOLS`에서 `Task` 제거, `VERIFY_AGENTS`에 `integrator` 추가, 프로필 비교 반전, `[review-ok]` 검사 무력화)을 임시 사본에 넣어 확인했고 전부 실패로 잡힌다.

## 6. 미해결

- Codex의 발행 도구 이름은 실측하지 않았다. tier-gate와 같은 매처(`Agent|Task|spawn_agent`)를 걸어 두며, 어긋나면 발화하지 않을 뿐 차단은 생기지 않는다(fail-open).
- 이 설치처는 `개인`이라 **차단 경로를 실사용 상태로 관측할 수 없다**. 회귀 테스트는 임시 REGISTRY.md로 `사내`를 구성해 판정하며, 실환경 관측은 사내 설치처의 첫 사용 시점으로 남는다.
