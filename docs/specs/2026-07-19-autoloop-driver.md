# 스펙: autoloop — 자율 멀티세션 루프 드라이버

- 날짜: 2026-07-19 / 상태: 확정
- 관련: ADR 025(아키텍처 결정), 루트 AGENTS.md §3(안전 가드레일)·§13(SDD/TDD), carryover 스킬(노트 템플릿 차용)

## 배경

한 세션 컨텍스트를 넘는 작업(멀티세션 완주·자율 개발)을 무인으로 돌리려면 세 가지가 필요하다: ① 반복 사이 프롬프트 재구성, ② 작업 중 사용자 질의 제거, ③ 컨텍스트 소진 시 자동 핸드오프 후 새 컨텍스트로 재개("wrapup→clear→재개"). ③이 핵심 공백이다 — `/clear`는 CLI 명령이라 세션 안의 모델이 스스로 부를 수 없다. 해법: **세션 바깥의 드라이버 프로세스가 `claude -p`(headless)를 반복 기동**하면 새 프로세스=새 컨텍스트가 되어 clear가 구조적으로 해결된다. 반복 간 상태는 carryover 노트(로컬 Markdown)로 넘긴다.

리스크는 코드가 아니라 게이트다: (a) 무인 모드가 하네스의 소프트 게이트(리뷰·신선한 증거)를 건너뛰어 결함이 누적되고, (b) 정지 조건이 없으면 토큰을 무한 소각하며, (c) 질의 제거를 permission 전면 bypass로 구현하면 §3(파괴적 작업은 예외 없이 사용자 확인)과 충돌한다. 이 스펙의 본체는 그 3개 게이트의 계약이다.

## 목표

- 사용자가 스펙 파일 하나를 지정해 루프를 기동하면, 사용자 개입 없이 반복(구현→검증→핸드오프)이 진행되고, 완료·차단·정체·상한 중 하나로 반드시 종료된다.
- 파괴적 명령은 무인 상태에서 직접 호출이 차단된다(협소 화이트리스트 + 블랙리스트 + headless 기본 거부) — 세션이 blocked를 보고하면 루프가 멈추고 사용자에게 이월된다. **완전 봉쇄는 아니다**: 테스트 실행은 곧 저장소 코드 실행이므로, bare 인터프리터 그랜트 금지(R3)로 우회면을 줄이되, 인프라·배포가 걸린 스펙에는 이 도구를 쓰지 않는 것이 사용 가드레일이다(SKILL.md 주의).
- 각 반복의 완료 주장은 드라이버가 **독립 실행한 테스트 출력**으로만 인정된다(모델 자가보고 불신).
- 사용자는 별도 세션에서 진행 상태를 확인하고 안전하게 정지시킬 수 있다.

## 비목표

- **전면 무인 승인 아님**: `--dangerously-skip-permissions` / `bypassPermissions`는 어떤 경로로도 쓰지 않는다(§3 완화 불가).
- **wrapup/carryover 스킬 대체 아님**: 대화형 세션의 수동 이월은 기존 스킬 그대로. autoloop은 자체 노트 파일을 쓴다(스키마만 차용).
- **오케스트레이션 대체 아님**: 반복 안에서의 팀 구성·검증 라우팅은 headless 세션이 로드하는 하네스(CLAUDE.md/AGENTS.md)가 담당한다. 드라이버는 반복 경계만 관리한다.
- **크로스 머신 아님**: 산출물은 `_workspace/`(미추적) — 같은 머신 한정. 정식 추적은 work-tracker의 몫.
- **Codex 안전 게이트는 sandbox 레벨(coarser)**: Codex 엔진은 fine-grained allow/deny 목록이 없다 — `--sandbox workspace-write`(구현)·`read-only`(검증)로 매핑한다. workspace-write는 쓰기를 워크스페이스에 confine하고, **네트워크는 기본값으로만 차단된다** — 설치처 `~/.codex/config.toml`의 `[sandbox_workspace_write] network_access`가 이 기본값을 덮을 수 있고 드라이버는 그 값을 고정하지 않는다(R3-2). 즉 원격 파괴 작업(kubectl·aws·terraform·gh·push) 봉쇄는 **설치처 설정에 달린 조건부 성질이지 이 도구가 보장하는 것이 아니다.** 그 위에 **워크스페이스 내 로컬 파괴 명령(예: 프로젝트 파일 rm)까지 정책으로 막지는 못한다**(Claude 블랙리스트와의 잔여 갭). 그래서 Codex 엔진도 인프라·배포 스펙 금지·완주 후 백업 전제는 동일하고, blocked 이월 메커니즘이 1차 방어다.
- **비용 정밀 회계 아님**: 반복 상한이 1차 백스톱이고 비용 상한은 결과 JSON이 제공될 때만 동작하는 보조 장치다.
- **단일 컨텍스트 작업 대상 아님 (비용 경계)**: 한 컨텍스트 윈도우에 들어가는 작업은 `/loop`·단일 세션이 더 싸다 — `-p` 반복의 재확립 비용(AGENTS.md 재주입·재탐색·검증 세션)은 **윈도우를 넘길 규모에서만** 회수된다. autoloop은 그 규모의 무인 작업 전용이다.
- **티어→모델 해석을 드라이버가 하지 않음**: 드라이버는 역할별 티어를 **선언·라우팅**만 하고(구현=implement, 검증=design), 티어→구체 모델명 매핑은 기동 세션이 §9 라인업 판단으로 수행한다 — 독립 스크립트에 모델명을 박지 않는다(탈모델명). 세션이 값을 안 넘기면 균일/기본으로 동작한다(강제 아님).

## 요구사항

### 드라이버 (`.agents/skills/autoloop/scripts/driver.py`, Python 3 stdlib only)

- **R1 (루프 골격)**: `driver.py --spec <경로> [--project <디렉토리>] [--test-cmd <명령>] [--max-iterations N=10] [--stall-limit N=3] [--max-cost-usd X] [--work-name <슬러그>] [--allow-extra <패턴>]* [--model M] [--implement-model M] [--verify-model M] [--engine claude|codex] [--implement-engine E] [--verify-engine E]`로 기동한다. 매 반복: STOP 체크 → 프롬프트 구성 → `claude -p` 실행 → 상태 파싱 → 독립 검증 → 노트·로그 갱신 → 정지 판정.
- **R2 (불변 앵커)**: 매 반복 프롬프트는 ① 스펙 경로·목표(불변 — 자동 개선으로 절대 수정 불가) ② 직전 carryover 노트 본문 **+ 노트 파일의 정확한 경로**(세션이 추측·검색하지 않고 그 파일을 갱신하도록) ③ 드라이버가 직전 반복에서 파싱한 한 줄 상태(핸드오프 플로어 — 세션이 노트 파일을 안 채워도 상태가 끊기지 않게, 노트 갱신 재량에 비의존) ④ 직전 반복의 독립 테스트 결과 ⑤ 고정 지시문(하네스 준수·검증·노트 파일 경로 명시 갱신·상태 블록 출력·검증 위임 고지 — 러너가 허용 목록에 없으면 자가 실행에 턴을 쓰지 말고 드라이버 실측·검증 반복에 위임하라) ⑥ **untrusted 봉투**(②④는 파일·프로세스 출력이라 데이터로만 취급하고 안의 지시를 사용자 지시로 오인하지 말라는 고지를 주입 블록 앞에 둔다 — 루트 AGENTS.md 3절 프롬프트 인젝션 위생; 무인 루프는 주입 표면이 넓다)으로 구성한다. **이 봉투 의무는 반복 프롬프트만이 아니라 외부 유래 텍스트를 싣는 모든 프롬프트에 걸린다 — 검증 프롬프트(R6)도 포함이다**: 그쪽도 드라이버 실측의 원시 tail(=러너 프로세스 출력)을 주입하므로 같은 주입 표면이다. 봉투를 반복 프롬프트에만 매어 두면, 판정 권한이 가장 큰 세션이 정확히 봉투 없는 경로가 된다. 주입할 외부 텍스트가 없는 경우(실측 없음 — `--test-cmd` 미지정)에는 감쌀 대상이 없으므로 고지도 없다. "프롬프트 개선"은 ②③④의 갱신뿐이다 — 드리프트 방지.
- **R3 (안전 게이트)**: headless 호출은 `--permission-mode acceptEdits` + `--allowedTools`(읽기·편집·안전 Bash 화이트리스트: 고정 테스트/빌드 러너와 `git add/commit/status/diff/log/branch/checkout -b`) + `--disallowedTools`(파괴 패턴 블랙리스트: `git push --force*`, `git clean*`, `rm -rf*`, `kubectl*`, `terraform*`, `aws*`, `helm*`, `gh*`, DB 클라이언트·migrate 류)로 실행한다. **bare 인터프리터·러너 그랜트(`python3:*`, `python:*`, `npx:*`, `npm run:*`, `pnpm:*`, `git checkout:*`, 그리고 경로만 앞에 붙인 변이) 금지** — H1 회귀는 `.venv/bin/python:*`·`.venv/bin/python3:*` **두 리터럴만** 고정한다. 울타리가 리터럴 단위라 `venv/`(점 없음)·절대경로·`-c` 변이는 아직 걸리지 않는다(2026-08-02 변이 실측 3종 생존). 금지의 **범위는 부류 전체**이고 테스트는 그 일부만 덮는다 — 구조적 검사(명령어의 basename이 인터프리터면 고정된 `-m pytest` 잔여를 요구)는 미구현이다. — 임의 코드 실행으로 블랙리스트를 감싸 우회하면 게이트가 지시 수준으로 격하된다. **미해소 갭 ④(venv 러너를 `--allow-extra`로 그랜트할 때, 실행되는 프로그램이 세션의 쓰기 표면 안에 있다)**: 이 워크스페이스의 표준 형태는 R18의 새 worktree에 venv를 만들어 `--test-cmd '.venv/bin/python -m pytest'`로 도는 것이다. 그 러너를 세션에도 그랜트하면(`--allow-extra`) 다른 항목과 성질이 하나 달라진다 — **허용되는 프로그램 자체가 세션이 `Write`로 덮어쓸 수 있는 파일이다**(`Write`는 범위 제한 없고 `acceptEdits`가 걸려 있다). 블랙리스트는 명령 문자열을 보지 실행된 프로그램의 행위를 보지 않으므로, 덮어쓴 뒤 허용 패턴에 맞는 문자열로 부르면 실행되는 것은 자기가 쓴 스크립트다. **능력이 늘지는 않는다** — 테스트 파일을 편집할 수 있는 세션은 기존 `pytest:*`만으로도 `conftest.py`·플러그인 자동 로드로 동일한 임의 코드 실행에 닿는다(15행 "완전 봉쇄는 아니다"). 늘어나는 것은 **탐지 실패의 겹수**이고 세 겹이다 — ① 테스트 파일이 아니라 R17 래칫과 검증 세션의 시야 밖이다(둘은 완료 기준마다 살아 있는 단언을 *테스트 파일*에서 찾는다); ② `.venv/**`는 프로젝트 gitignore 대상이라 어떤 diff에도 안 뜬다(테스트 파일 훼손은 `git diff`에 떠서 PR에서 보인다); ③ **드라이버 자신의 실측이 같은 경로로 돈다** — `run_test_cmd`는 `subprocess.run(cfg.test_cmd, shell=True, cwd=cfg.project)`로 같은 문자열을 같은 디렉터리에서 돌리고 green/red를 종료 코드만으로 판정하므로(R5-1), 덮어쓴 것이 0으로 끝나면 드라이버가 green을 기록한다. **③만 관측성이 아니라 증거 자체의 문제다** — R5의 "이 결과만이 증거다"가 서 있는 바닥이 세션의 쓰기 표면 안에 있다는 뜻이다. **③은 그랜트가 만드는 것이 아니다**: venv 기반 `--test-cmd`와 범위 없는 `Write`의 조합에서 나오며, 세션에 러너를 전혀 주지 않아도 성립한다(드라이버 실측은 도구 목록을 아예 참조하지 않는다 — 독립 검증으로 확인). **위협 모형은 미해소 갭 ③·R17과 같은 가족이다** — 게이트의 입력을 게이트 대상이 편집할 수 있다. 세 지점이다: 테스트 파일(R17), `state.json`(갭 ③), venv 러너(갭 ④). **좁히지 않은 이유와 좁힌다면**: 경로별 편집 금지(`Write`를 `.venv/**`에 거부)가 근본책이나 CLI 도구 패턴에 그 표현이 없다. 관측되지 않은 위협이라 선제 장치를 신설하지 않았다(갭 ③과 같은 처리). 값싼 후보는 **기동 시 러너 파일의 해시를 고정해 두고 매 반복 실측 전에 대조, 달라졌으면 green이 아니라 `error`로 분류**하는 것이다 — `error`는 이미 "증거의 부재"를 뜻하는 라벨이라 의미가 맞고 R19의 기동 검사와 같은 자리에서 값을 얻는다. 프로젝트별 러너가 더 필요하면 `--allow-extra`(반복 가능)로 **사용자가 명시 그랜트**하며, 검증 세션(readonly)에는 확장 그랜트를 주지 않는다. 세션이 `blocked` 상태를 보고하면 드라이버는 즉시 정지하고 노트에 "사용자 확인 필요" 항목을 남긴다.
- **R3-1 (설정 소스 격리 — 위 목록이 실제 게이트가 되기 위한 전제)**: Claude 헤드리스 호출은 `--setting-sources project`로 실행해 **설치처 사용자 설정(`~/.claude/settings.json`)을 상속하지 않는다.** 상속하면 게이트가 두 방향으로 무너진다 — ① `permissions.allow`가 병합돼 R3이 금지한 bare 인터프리터 그랜트가 되살아나고, ② Bash 명령을 재작성하는 `PreToolUse` 훅(프록시 래퍼 류)이 있으면 재작성된 문자열이 SAFE_ALLOW 어디에도 안 맞아 **허용이 무효화되는 동시에 DESTRUCTIVE_DISALLOW도 함께 빗나간다**. `project`를 남기는 이유는 하네스 항상-온 로드(§12)이며, 소스를 전부 비우면 항상-온이 로드되지 않는다. 훅은 재작성만 하는 것이 아니라 `permissionDecision: allow`로 **허용을 부여**할 수도 있다(실측: 러너 2종) — 즉 사용자 설정을 상속하면 목록보다 상위의 판정 권한이 게이트 위에 얹힌다. 따라서 **`project` 소스에도 Bash를 재작성하거나 허용을 부여하는 훅을 등록하지 않는다**가 이 요구사항이 서 있기 위한 불변식이다(하네스 루트 `.claude/settings.json`은 추적되므로 리뷰로 지킨다).
- **R3-1 부수 효과(의도된 것 + 조용한 것)**: ① 사용자 전역 허용으로 무인 세션이 얻던 명령은 더 이상 딸려오지 않으므로, 프로젝트 러너는 `--allow-extra`로만 들어온다. ② **사용자·플러그인 스킬이 세션에서 사라진다**(실측: `orca-cli`·`watch` 미가용, 하네스 `orchestrate`는 유지). 루트 §11이 외부 도구 스킬을 전역 설치로 규정하므로 **무인 세션에서는 외부 도구 스킬이 하나도 닿지 않는다.** 이 손실은 오류로 드러나지 않고 조용하므로, 외부 스킬에 의존하는 스펙은 이 루프의 대상이 아니다.
- **R3-2 (Codex 경로는 이 격리가 적용되지 않는다 — 미해소 갭)**: `build_codex_args`는 `-c`/`--profile`을 넘기지 않으므로 Codex는 설치처 `~/.codex/config.toml`을 그대로 상속한다. `--sandbox workspace-write`가 `sandbox_mode`는 덮지만 `[sandbox_workspace_write]` 테이블은 덮지 않는다. **이 설치처는 `network_access = true`이므로 "workspace-write는 네트워크 기본 차단"이라는 전제가 성립하지 않는다** — Codex는 fine-grained denylist가 없어 네트워크 차단이 원격 파괴 조작을 막는 유일한 수단이었다. 코드 대응은 `-c sandbox_workspace_write.network_access=false` 고정이지만, **이 변경에서는 적용하지 않았다**: 런타임 효과를 측정하지 않았고(미검증 범위), 키 경로가 어긋나면 조용히 무효가 되어 지금보다 나쁜 상태(막힌다고 적힌 채 안 막힘)가 된다. 같은 상속 표면에 **`~/.codex/hooks.json`(사용자 레벨 `PreToolUse`/`PermissionRequest`/`PostToolUse`)** 도 있다 — R3-1이 Claude 쪽에서 막은 원인 B의 구조적 대응물이며, 현재 설치처의 것은 관측용으로 양성이나 격리되지 않은 표면이라는 사실은 같다. 해소 전까지 **Codex 엔진 사용 시 설치처의 `network_access`와 `hooks.json`을 먼저 확인**하는 것이 사용 가드레일이다.
- **R4 (상태 계약)**: 세션은 최종 출력 끝에 ```json 펜스로 `{"status": "done"|"continue"|"blocked", "open_items": <int>, "note": "<한 줄>"}` 블록을 출력하도록 지시받는다. 드라이버는 **마지막** 유효 블록을 채택하고, 파싱 실패 시 `continue`로 간주하되 연속 2회 파싱 실패면 정체로 취급한다.
- **R5 (독립 검증)**: `--test-cmd`가 주어지면 드라이버가 매 반복 종료 후 대상 디렉토리에서 직접 실행해 exit code·출력 tail을 기록한다. 세션의 "테스트 통과" 주장과 무관하게 이 결과만이 증거다(§13).
- **R5-1 (실행 결과 3분류 — 러너 고장과 테스트 실패는 다른 원인이다)**: 테스트 결과는 `green`(exit 0) / `red`(exit≠0) / **`error`**(드라이버가 명령을 **실행조차 못 함** — 타임아웃, `OSError`, 그리고 셸 종료 코드 **126**(실행 불가)·**127**(명령 없음)) 셋으로 분류한다. **이 분류기는 반복마다만이 아니라 기동 시에도 돈다**(R19) — 실행·분류를 한 함수(`run_test_cmd`)로 두고 기동 검사와 루프가 그것을 **공유한다**. 사전 검사에 두 번째 분류기를 두면 안 되는 이유는 성능이 아니라 판정 일치다: 둘이 드리프트하면 **"실행할 수 없다"의 뜻이 기동과 루프에서 갈라져**, 기동이 통과시킨 명령이 루프 안에서는 `error`로 기록되거나(그러면 R19가 막으려던 런이 그대로 돌고) 그 반대가 된다(멀쩡한 명령으로 기동이 거부된다). 어느 쪽이든 조용히 어긋나고, 어긋난 뒤에는 로그만 보고는 어느 분류기의 판정인지 알 수 없다. **셸 코드를 함께 봐야 분류가 실제로 선다**: 실행은 `shell=True`이므로 없는 명령은 `OSError`가 아니라 셸이 127로 돌려주며, 예외만 보면 오타 난 `--test-cmd`가 그대로 `red`로 들어와 이 요구사항이 겨냥한 사례를 하나도 잡지 못한다. `error`를 `red`로 뭉개면 러너가 고장난 반복마다 세션이 "테스트가 깨졌다"는 증거를 받아 **멀쩡한 제품 코드를 고치며 반복 예산을 전부 태운다**(원인이 여러 개일 때 갈래를 나누지 않은 루프의 전형적 실패). 갈래별 처리: ① `error` 반복의 프롬프트에는 "러너 실행 실패이며 실패한 테스트가 아니다 — 이걸 쫓아 제품 코드를 고치지 말라"는 라벨을 붙여 주입한다. ② `done` 확정은 `green`에서만 가능하다(`error`는 green이 아니다 — 증거 부재). ③ `red`·`error`에서 `green`으로의 전환은 진전으로 센다. ④ 연속 2회 `error`는 R7⑦로 종료한다. 분류 근거는 **드라이버가 확실히 아는 사실**(자기 subprocess가 뜨지 못했다)로 한정하고, 러너 출력 문자열을 해석해 원인을 추정하지 않는다 — 프레임워크별 휴리스틱은 조용히 틀린다. **같은 근거로 `error` 결과에는 실패 방식 라벨(`kind`)을 함께 남긴다** — `timeout`(실행은 됐으나 상한 안에 끝나지 않음)과 `unrunnable`(뜨지도 못함: 셸 126·127·`OSError`) 둘이다. 이것도 러너 출력 해석이 아니라 **자기 호출이 어떻게 실패했는지**라 위 원칙 안에 있으며, 처방이 서로 다른 두 갈래를 거부 메시지에서 가르는 데 쓴다(R19). **`outcome` 은 여전히 셋이다** — `kind` 는 `error` 안의 하위 구분이지 넷째 결과가 아니고, 진전 판정(R7③)·done 게이트(R6)·R7⑦은 `kind` 를 보지 않는다(증거가 없다는 결론은 두 갈래가 같다).
- **R6 (완료 판정)**: `done` 확정 조건 = 세션 status `done` **and** open_items 0 **and** 독립 테스트 green(test-cmd 있을 때). 확정 전에 **검증 반복**을 1회 돌린다 — 읽기 전용 reviewer 지시문의 별도 `claude -p`가 스펙 완료 기준 대비 PASS/BLOCK을 판정하고, BLOCK이면 사유를 다음 반복 입력에 넣고 루프를 계속한다(잔여 반복 내에서). **기능별 모델 티어(§9)**: 검증 반복 = **design 티어**(reviewer 역할 — 최고 성능), 구현 반복 = **implement 티어**(표준). 드라이버는 이 역할→티어를 `resolve_model`로 구분해 `--verify-model`(design)·`--implement-model`(implement)을 각 `claude -p`에 적용한다. **§9 탈모델명 준수**: 드라이버 코드엔 모델명이 없고, 티어→모델 해석은 **기동 세션(SKILL.md start)이 현재 CLI 라인업에서** 수행해 값으로 넘긴다. 역할별 미지정 시 균일 `--model`로, 그것도 없으면 세션 기본 상속으로 폴백한다. 경량 모델은 검증에 금지(§9·사용자 전역 정책).

  **검증 세션은 그 반복의 드라이버 실측(R5)을 함께 받는다 — 구현 세션의 주장이 아니라 드라이버 자신의 측정치로 명기해서.** 프롬프트에는 결과 라벨과 원시 tail을 싣고, 드라이버가 그 세션이 끝난 뒤 대상 디렉터리에서 세션 통제 밖으로 직접 실행한 값임을 말한다. **`READONLY_ALLOW`를 넓혀 검증 세션이 직접 돌리게 하는 것은 해법이 아니다** — 그러면 판정자가 **자기가 만든 결과로 판정**하게 되어, 이 측정치가 존재하는 이유인 독립성이 사라진다. 즉 이 조항은 권한 확대의 **대체재**이지 그 전 단계가 아니다. 없으면 어떻게 되는지는 실측됐다(2026-08-02 런): 읽기 전용이라 스위트를 못 돌린 검증 세션이 "pytest 실행이 거부돼 완료 기준 1(전 테스트 통과)을 직접 재지 못했다"를 BLOCK 사유로 적었는데, 드라이버는 그 값을 이미 독립 실행으로 갖고 있었다.

  **프롬프트는 그 값이 정하는 것과 정하지 않는 것을 갈라 싣는다 — 이건 R17 래칫의 하드닝이다.** 정하는 것은 스위트가 green으로 도는가 하나뿐이고, **완료 기준이 테스트로 덮였는지는 정하지 않는다.** 그래서 실측 green은 R17의 래칫 검사(완료 기준마다 살아 있는 단정을 눈으로 확인)를 면제하지 않으며, 단정을 지우거나 속을 비운 기준도 여전히 GREEN으로 측정된다는 것을 프롬프트가 명시한다. 이 문장이 없으면 실측을 주는 것이 **래칫을 무력화하는 방향으로** 작동한다 — 판정자가 green을 커버리지 증거로 읽으면 R17이 겨냥한 회피가 바로 그 경로로 통과하고, 래칫이 존재하는 이유가 정확히 green≠커버리지이기 때문이다.

  **런타임에 검증 세션에 닿는 값은 `green`과 '실측 없음' 둘뿐이다.** 검증 반복은 done 게이트를 통과해야 돌고 그 게이트가 `last_test is None or outcome == "green"`이므로, `red`·`error`는 애초에 검증 세션까지 오지 못한다. 프롬프트 조립부는 세 라벨을 모두 표현할 수 있고 테스트도 셋을 덮지만(게이트가 바뀌면 그때 맞는 문구가 나오도록), **"검증 세션이 red/error 실측을 보고 판정한다"는 서술은 사실이 아니다** — 이 스펙이 그렇게 읽히면 다음 독자가 없는 경로를 근거로 판단한다. `--test-cmd` 미지정 런에서는 실측이 아예 없으므로, 그 경우 프롬프트는 **측정치가 없다는 사실**을 싣고 읽어서 확인할 수 없는 기준은 BLOCK하라고 지시한다(없는 측정을 통과로 읽히게 두지 않는다).
- **R7 (정지 조건 — 반드시 하나로 종료)**: ① done 확정 ② blocked ③ 정체(연속 `--stall-limit`회 진전 없음 — 진전 = open_items 감소 또는 테스트 결과 개선(red·error→green 전환)) ④ `--max-iterations` 소진 ⑤ STOP 파일 감지 ⑥ 비용 상한 초과(결과 JSON의 `total_cost_usd` **누적 — R16에 따라 재기동을 넘어 합산**, 제공될 때만) ⑦ **헤드리스 세션 실행 연속 2회 실패 또는 테스트 러너 실행 연속 2회 실패**(둘 다 "드라이버가 자기 subprocess를 띄우지 못함"이라는 같은 부류라 사유를 나누지 않는다 — 어느 쪽인지는 로그 줄과 노트가 나른다). 각 종료 사유를 노트·로그에 명시한다. **정지 사유는 이 7개로 고정한다** — 갈래를 늘리는 대신 로그가 세부를 나르게 해 "반드시 하나로 끝난다"는 계약을 단순하게 유지한다.
- **R8 (산출 구조)**: `_workspace/autoloop/<작업명>/` 아래 — `carryover.md`(핸드오프 노트: 한 일/다음/막힘/사용자 확인 필요/참조), `driver.log`(반복별 타임스탬프·상태·정지 판정), `iters/iter-N.json`(반복별 원시 결과 메타 — 단, claude 프로세스 실패 반복은 로그 줄로만 기록. **N은 런당 반복 번호가 아니라 누적 반복 수다** — 런당 번호는 재기동마다 1로 돌아가므로 같은 `--work-name` 재기동이 직전 런의 `iter-1.json`을 조용히 덮어써 감사 기록이 사라진다. `driver.log`는 둘을 함께 적는다), **`state.json`**(R16 실행 위치 체크포인트 — 기계 판독용이며 사람이 읽는 서술은 `carryover.md`의 몫이다. 쓰기는 `state.json.tmp` 경유 원자 교체라 그 임시 파일이 남아 있으면 안 된다), `STOP`(존재하면 다음 반복 경계에서 안전 종료 후 드라이버가 삭제하지 않고 보존). 같은 디렉터리에 스킬(드라이버 아님)이 기동 시 `launch.log`(매 기동 truncate — 종료 줄 `[autoloop] 종료: <사유>`가 여기 남는다)와 `driver.pid`를 쓴다. **종료 감시는 `driver.log`가 아니라 `launch.log`를 본다** — `driver.log`는 append 전용이라 R10 재개 시 이전 런의 EXIT 줄이 그대로 남아 감시가 즉시 자기충족한다.
- **R9 (기동 사전 검사)**: 스펙 파일 존재 + "완료 기준" 절 존재를 확인하고, 없으면 기동 거부(완료 판정 오라클 없는 루프 금지). `--test-cmd` 미지정 시 경고를 로그·stdout에 남긴다(증거 약화 모드).
- **R10 (재개성)**: 같은 `--work-name`으로 재기동하면 기존 `carryover.md`**와 R16 실행 상태**를 이어받아 계속한다(STOP 파일이 있으면 삭제 후 진행할지 묻지 않고 **기동 거부** — 명시적 STOP 해제는 사용자 몫).
- **R16 (실행 위치 체크포인트 — 재기동이 게이트를 초기화하지 않는다)**: 반복 경계마다 `state.json`에 실행 상태를 **원자적으로**(임시 파일 + `os.replace`) 기록하고, 기동 시 읽어 이어받는다. 대상: 누적 반복 수·누적 비용·정체 카운터·직전 open_items·**직전 테스트 결과의 라벨**(`green`/`red`/`error`)·최초 유효 반복 여부(`seen_valid`)·미소진 reviewer 피드백·직전 상태 한 줄·직전 종료 사유.

  **라벨은 이어받고 본문(출력 tail)은 안 이어받는다 — 의도된 비대칭이고 대가가 있다.** 진전 판정(R7③)은 `red`·`error`→`green` 전환을 봐야 하므로 라벨이 필요하지만, tail은 이 런에서 실측한 것만 증거다(R5). 그래서 **재기동 첫 반복의 프롬프트 테스트 블록은 `(not yet run)`이 되고**, 직전 런이 red로 죽었다는 사실을 드라이버는 아는데 세션은 모른 채 시작한다 — R2④("직전 반복의 독립 테스트 결과")가 그 한 반복에서는 충족되지 않는다. 라벨만 문구로 실어 주는 선택지가 있지만, 근거 없는 tail 없이 "직전에 red였다"만 주면 세션이 무엇이 깨졌는지 모르고 추측하게 되므로 이 변경에서는 취하지 않았다. 손해는 재기동 첫 반복 1회분이다.

  **R19가 이 비대칭을 닫을 수 있어 보이지만 닫지 않는다(2026-08-02 검토·유지 결정).** R19의 기동 검사는 `--test-cmd`가 있으면 **이 런에서 실측한** 신선한 결과를 만들므로, 재기동 첫 반복의 `(not yet run)` 자리에 넣을 tail이 형식상 존재한다. 그럼에도 넣지 않는 이유는 **그 값이 무엇에 대한 증거인지가 다르기 때문**이다 — 기동 검사의 측정은 **어떤 세션도 돌기 전의 트리**에 대한 것인데, R2④와 R5가 말하는 것은 **직전 반복이 한 일**에 대한 측정이다. 프롬프트의 테스트 블록은 "the only trusted evidence"라는 라벨을 달고 있어, 거기에 반복 이전의 tail을 넣으면 세션이 그것을 직전 작업의 결과로 읽는다. 즉 빈 블록(정직한 무증거)이 낡은 블록(권위 라벨이 붙은 오독 유발)보다 낫다. **갭은 열린 채로 남으며 위 문단이 그 대가의 원본이다** — 다음 독자가 "왜 R19가 있는데 여기가 비었나"를 다시 묻지 않도록 검토됐음을 기록해 둔다.

  **누적 비용 판정은 기동 시점도 `>`(초과)로 둔다** — 정확히 상한과 같을 때 한 런이 더 시작되는 여유가 남는데, 런 내부 판정도 같은 `>`이므로 한쪽만 `>=`로 바꾸면 같은 상한에 두 기준이 생긴다. 부동소수 누적에서 정확히 일치하는 경우가 드물다는 점까지 합쳐, 비대칭을 만들지 않는 쪽을 택하고 여유 1런을 기록해 둔다(독립 검증 관찰 항목).

  **왜 필요한가 — R10이 노트만 물려받는 동안 게이트 전부가 재기동마다 0으로 돌아갔다.** ① 정체 카운터와 `seen_valid`가 리셋돼, 정체로 끝난 루프를 재기동하면 첫 반복이 **무조건 진전으로 인정**받고 정체 게이트(R7③)를 영구히 우회할 수 있었다. ② 누적 비용이 리셋돼 `--max-cost-usd`가 작업 예산이 아니라 런당 예산이 되어, 재기동 N회면 상한의 N배를 썼다. ③ reviewer BLOCK 사유(`feedback`)와 직전 상태 한 줄(핸드오프 플로어)이 사라져, 재기동 첫 반복은 **왜 BLOCK됐는지 모르는 상태로** 시작했다 — 노트에 남았을 수도 있지만 그건 세션 재량이고, 플로어는 바로 그 재량에 의존하지 않기 위해 존재한다. 무인 루프는 세션 한도·프로세스 강제 종료로 조용히 죽는 것이 정상 경로이므로, 재기동은 예외가 아니라 상시 경로다.

  **비용 상한은 작업 누적으로 해석한다**(사용자가 "이 작업에 최대 $X"라고 말한 것에 맞춘다). 누적이 이미 상한을 넘은 상태로 재기동하면 즉시 `cost`로 종료하며, 그 사유를 로그에 명시한다 — 계속하려면 `--max-cost-usd`를 올리거나 새 `--work-name`을 쓴다(예산을 지우는 별도 플래그는 두지 않는다 — 두 우회로가 이미 있고 플래그는 상한을 무심코 무력화하는 손잡이가 된다). **반복 상한(`--max-iterations`)은 런당으로 유지한다** — 폭주 프로세스에 대한 런당 백스톱이 그 요구사항의 역할이고, 누적 반복 수는 로그·`status`가 보도록 기록만 한다.

  **`blocked`가 이 요구사항과 만나면 인터럽트가 된다**: 사용자 확인이 필요해 멈춘 루프가, 답을 받은 뒤 같은 `--work-name` 재기동으로 **정체·비용·피드백을 그대로 안고** 멈춘 자리에서 이어진다. 별도 장치가 아니라 R16의 부수 효과다.

  **`state.json`이 파싱 불가면 기동을 거부한다**(R9 검사에 합류 — 사유와 경로를 출력하고 사용자가 지우게 한다). 원자적 기록이라 부분 기록은 발생할 수 없으므로 파싱 실패는 정상 경로가 아니며, 여기서 fail-open하면 **이 요구사항이 막으려는 바로 그 조용한 게이트 초기화**가 된다.
- **R17 (테스트 래칫 — 실패하는 테스트를 고쳐 통과시키지 못하게)**: 세션은 **기존 테스트를 삭제·비활성(skip/xfail)·약화(단정 완화)해서 통과시키는 것이 금지**되며, 테스트 자체가 틀렸다고 판단하면 고치지 말고 `blocked`로 보고한다. 이 금지를 ① 반복 프롬프트의 고정 지시문과 ② 검증 세션(R6)의 BLOCK 조건 양쪽에 싣는다. 검증 세션은 **완료 기준마다 그것을 실제로 검사하는 살아 있는 단정이 있는지**를 확인하고, 없거나 비활성화돼 있으면 BLOCK한다.

  **왜 필요한가**: R5의 독립 테스트 실행이 증거인데, 세션에는 `Edit`·`Write`가 열려 있고 `acceptEdits`로 자동 승인된다 — 즉 실패하는 단정을 지우면 드라이버의 `--test-cmd`가 exit 0이 되어 **게이트가 스스로 green을 보고한다.** 무인 루프에서 이 회피는 관측되기 어렵다.

  **미해소 갭 ①(발동 지점이 done 게이트뿐이다 — 이쪽이 더 크다)**: 래칫 검사는 **`done` 주장이 확정되기 전에만** 돈다(R6 검증 세션). 그런데 진전 판정(R7③)은 `red`·`error`→`green` 전환을 진전으로 세므로, 세션이 정체 직전마다 단정 하나씩을 약화해 green을 만들면 **정체 카운터가 리셋되고 `done`을 주장하지 않은 채 `exhausted`로 끝난다** — 검증 세션이 한 번도 돌지 않아 래칫이 발동하지 않고, 사용자에게는 "테스트 green"으로 보고된다. 진전 판정에 래칫을 붙이는 것은 매 반복 검증 세션을 돌리는 비용이라 채택하지 않았고, 대신 **`status` 리뷰 시점의 튜닝 신호**(SKILL.md — 「Ratchet evasion」)로 사람이 잡게 두었다. 즉 R17은 *done 경로의 하드닝*이고 *green 보고 전반의 보증은 아니다*.

  **미해소 갭 ②(기계적 diff가 없다)**: 드라이버가 테스트 파일을 diff하지 않는다. 검증 세션의 cwd는 하네스 루트이고 `READONLY_ALLOW`의 git 항목은 `Bash(git status:*)`·`Bash(git diff:*)`·`Bash(git log:*)` 셋인데 모두 하위 명령이 바로 붙는 형태라, 프로젝트 저장소를 보려면 `git -C <경로> diff`가 되어야 한다. **허용 패턴이 문자열 접두 매칭이라는 것은 이 스펙의 2026-07-26 실측이 성립하기 위한 전제이지 그 실측이 직접 잰 값은 아니다**(그때 잰 것은 `PreToolUse` 훅이 명령을 재작성하면 허용과 차단이 함께 빗나간다는 것이고, 그 결론은 매칭이 접두 기준일 때만 성립한다). `git -C … diff` 형태를 헤드리스 프로브로 재현하지 않았으므로 **전제·결론 모두 이 변경에서는 미검증**이다. 그럼에도 패턴을 `git -C`까지 넓히는 대응은 취하지 않는다 — 같은 접두 성질이면 `git -C <경로> push --force`가 `DESTRUCTIVE_DISALLOW`도 함께 빗나가므로, 래칫을 얻으려고 블랙리스트에 구멍을 내는 교환이 된다(전제가 틀렸다면 넓힐 필요 자체가 없다 — 어느 쪽이든 넓히지 않는 것이 옳다). 그래서 래칫은 **읽기 도구(Read/Glob/Grep — 경로 기반이라 절대경로로 프로젝트를 그대로 읽는다)로 테스트 파일을 직접 읽는 design 티어 리뷰어의 판정**에 의존하며, 하드 게이트가 아니다. R3-2와 같은 등급의 남은 갭으로 기록한다.

  **미해소 갭 ③(`state.json`이 세션의 쓰기 표면 안에 있다)**: R16의 체크포인트는 `_workspace/autoloop/<작업명>/`에 있고, 무인 세션은 `SAFE_ALLOW`의 `Edit`·`Write`를 `acceptEdits`로 쥐고 있으며 그 디렉터리 경로는 지시문 4항이 노트 경로로 이미 알려준다. 즉 **세션이 자기 정체 카운터·누적 비용을 낮춰 쓰는 것을 정책으로 막지는 못한다** — R17과 같은 위협 모형(게이트의 입력을 게이트 대상이 편집할 수 있다)이다. 코드로 좁히려면 편집 허용을 경로별로 갈라야 하는데 CLI 도구 패턴에 그 표현이 없어 이 변경에서는 취하지 않았고, 관측되지 않은 위협이므로 방어 장치를 선제 신설하지도 않았다(패턴 읽기 수준의 판단이고 프로브로 재현하지 않았다). **탐지 경로는 `driver.log` 안에서만 성립한다**: 로그는 append 전용이므로 직전 런의 `EXIT … total_cost=… total_iterations=… stall=…` 줄과 다음 런의 `START … resumed(…)` 줄을 비교하면 두 런 사이에 `state.json`이 손대졌는지 드러난다. **`resumed(…)`를 `state.json`과 비교하는 것은 탐지가 아니다** — 그 줄은 방금 읽은 그 파일에서 출력되므로 어긋날 수가 없고, 그렇게 적으면 조작된 상태에서 오히려 "정상" 판정이 나온다(초안이 그렇게 적었고 독립 검증이 실측으로 잡았다). 이 비교가 서기 위해 `EXIT` 줄에 `stall`을 함께 싣는다 — 정체 카운터가 가장 낮춰 쓰기 쉬운 값인데 그 전까지는 로그에 흔적이 없었다.

- **R18 (작업 위치 격리 — 무인 루프는 전용 worktree 에서만 돈다)**: `--project`가 **연결된 worktree 가 아닌 git 저장소**면 기동을 거부한다. 판정은 기계로 한다 — `git -C <대상> rev-parse --git-dir --git-common-dir` 두 값을 각각 대상 경로 기준으로 join 한 뒤 realpath 로 정규화해 비교하고, **다르면 연결된 worktree**(git-dir 만 `.git/worktrees/<이름>`으로 갈린다), **같으면 아니다**. 겨냥하는 것은 `project/<이름>/` 공유 체크아웃이지만 **판정은 그보다 넓다** — bare·서브모듈·중첩 저장소도 함께 거부된다. 좁히려면 대상이 어떤 종류의 저장소인지 분류해야 하는데 그 분류는 틀릴 때 조용히 통과시키는 쪽으로 틀리고, **거짓 거부는 worktree 를 만들면 풀리지만 거짓 통과는 밤새 남의 체크아웃을 움직인다.**

  **면제는 둘뿐이다.** ① git 저장소가 아니면 격리할 브랜치 자체가 없다. ② 대상의 git-common-dir 이 **이 드라이버 파일이 놓인 하네스 저장소의 것과 같으면** 면제한다(루트는 main 직커밋이 규칙 — 루트 §5. `_workspace/` 아래 샌드박스 스펙도 이 경로로 들어온다). **기준점을 `os.getcwd()`로 잡으면 안 된다** — 그건 사용자가 어디서 기동했는지일 뿐이라 하위 프로젝트 안에서 기동하는 것만으로 그 저장소가 "루트"가 되어 면제가 자기 자신에게 발동하고, 게이트가 통째로 무효가 된다(독립 검증 F1 실측). 드라이버 파일의 위치는 설치 구조상 하네스 저장소 안이므로 그쪽이 고정점이다. **`GIT_DIR`·`GIT_COMMON_DIR`·`GIT_WORK_TREE`·`GIT_INDEX_FILE`은 하위 프로세스 환경에서 제거한다** — 남겨 두면 rev-parse 가 대상 대신 그 값을 답해 두 값이 항상 같아지고 판정이 통과로 고정된다(검증 F5 실측).

  **판정 불가는 면제가 아니라 거부다.** 대상 디렉터리가 없거나 git 을 실행하지 못하면 거부한다 — 통과로 두면 R16 의 체크포인트를 fail-closed 로 둔 이유가 여기서 무너진다. "저장소가 아님"(rev-parse 가 exit≠0)과 "git 을 못 돌림"(`OSError`)은 갈라 다룬다.

  **worktree 생성은 드라이버가 아니라 기동 세션의 몫이고**(R11), Claude 엔진의 `SAFE_ALLOW`에 `Bash(git worktree:*)`를 추가하지 않는다 — 드라이버는 만들어졌는지만 판정해 무인 게이트를 넓히지 않는다. **Codex 엔진에는 이 문장이 성립하지 않는다** — 도구 목록 자체가 없고 안전 경계가 `--sandbox workspace-write`이므로 워크스페이스 안의 `git worktree`는 막히지 않는다(R3-2 와 같은 등급의 갭이며, R18 의 기동 거부는 엔진과 무관하게 선다). **우회 플래그는 두지 않는다**(R16의 예산 리셋 플래그를 기각한 것과 같은 이유 — 상한을 무심코 무력화하는 손잡이가 된다).

  **왜 필요한가**: 무인 세션은 `SAFE_ALLOW`의 `git add`·`git commit`·`git checkout -b`를 `acceptEdits`로 쥔 채 몇 시간을 돈다. 대상이 `project/<이름>/`이면 **사용자가 쓰던 체크아웃의 브랜치가 밤새 움직이고 그 위에 커밋이 쌓인다** — ADR 035가 "절차를 구조로" 바꿔 없앤 실패 모드를, 아무도 보고 있지 않은 동안 재현하는 것이다. 그리고 ADR 035의 발동 조건("파일을 바꾸는 작업")은 무인 루프에 그대로 해당하는데도 이 스킬만 그 조항 바깥에 있었다(실측 2026-07-30: SKILL.md 에 `worktree` 0건, `SAFE_ALLOW`에 `git worktree` 그랜트 0건 — 즉 세션이 규칙을 읽어도 만들 수가 없었다. 2026-07-26 런 `agent-eval-gate`가 `--project .../project/agent-eval-gate`로 40반복 상한을 걸고 돌았던 것이 `driver.log`에 남아 있다 — ADR 035 이전이라 당시 위반은 아니지만, 스킬이 오늘 그대로 재현할 형태다).

  **정리는 이 스펙의 몫이 아니다** — worktree 제거 판정의 정본은 `branch-workflow`이고(ADR 035 5항), 루프 종료 후 사용자 세션이 그 절차를 탄다.

- **R19 (테스트 명령 기동 검사 — 실행조차 못 하는 `--test-cmd` 로는 기동하지 않는다)**: `--test-cmd`가 **주어졌을 때만** 발동한다(미지정 루프는 이전과 동일하게 기동하고 R9의 증거 약화 경고만 받는다). 드라이버는 기동 사전 검사에서 그 명령을 **대상 디렉터리에서 1회 실행**하고, **R5-1의 분류기를 그대로 통과시켜**(별도 분류 로직을 만들지 않는다 — R5-1 공유 조항) 결과가 **`error`이면 기동을 거부한다.** 거부 사유에는 명령·대상 디렉터리·실패 사유를 함께 싣는다(어느 것 하나만 빠져도 사용자가 자기 체크아웃에서 다시 돌려 보고 "잘 되는데"로 끝난다). 검사 순서는 사전 검사의 **마지막**이다 — 이것만 실제로 스위트를 돌리므로, 값싼 거부 사유(스펙 부재·STOP·손상된 `state.json`·비-worktree 대상)가 먼저 걸러진 뒤에 실행한다.

  **`red`는 거부하지 않는다 — 이건 별도의 요구사항이지 위 조항의 예외 서술이 아니다.** 실패하는 스위트는 TDD 루프의 **정상 출발 상태**이므로(R5-1의 갈래 ③이 red→green 전환을 진전으로 세는 것과 같은 전제), 여기서 red를 막으면 이 도구의 **주 용도가 막힌다** — 통과하는 테스트를 먼저 만들어 놓아야 무인 루프를 돌릴 수 있다는 뜻이 되어 "실패 테스트 → 최소 구현 → 통과"(§13-2)와 정면으로 부딪힌다. `green`도 당연히 통과한다. **거부 조건만 적고 이 조항을 빼면 안 되는 이유**: 「실행 안 되면 거부」만 남으면 다음 편집자가 "안전한 쪽으로" 조건을 `!= green`으로 넓히는 것이 자연스러운 강화처럼 보이고, 그 한 글자가 도구를 못 쓰게 만든다. 그래서 통과 조건을 요구사항으로 못 박고 완료 기준에서도 따로 검사한다.

  **왜 필요한가 — 기동자가 사용자와 명령을 합의하는 것으로는 안 잡힌다.** 실측(2026-08-02): `--test-cmd '.venv/bin/python -m pytest …'`로 새 worktree(R18)를 대상으로 기동한 런에서 `.venv`가 gitignore라 **구조적으로** 없었고(우연한 오타가 아니다 — 새 worktree에는 gitignore된 산출물이 원리적으로 없다), 매 반복이 셸 127로 `test=error`를 기록했다. 그 런은 **검증할 수 없는 한 반복에 $15를 태우고** 두 반복 뒤 `blocked`로 멈췄다. 기동자는 명령을 사용자와 확인했지만 **한 번도 실행해 보지 않았다.** R5-1·R7⑦이 그런 루프를 두 반복 만에 끝내 주긴 하지만, 그건 이미 예산을 쓴 뒤의 손실 제한이고 R19는 그 앞단이다 — **증거를 만들 수 없는 런은 시작하지 않는 것이 옳다.** 사용자 체크아웃에서 도는 명령이 루프 대상에서 안 도는 것이 이 실패의 형태이므로, 검사는 반드시 **대상 디렉터리에서** 돈다.

  **검사 순서(마지막)와 실행 위치(대상 디렉터리)는 비용이 아니라 안전 속성이다.** 검사가 앞에 오면 **거부될 기동에서 사용자가 준 임의의 셸 명령이 먼저 실행된다** — STOP 이 걸린 작업, 손상된 `state.json`, 그리고 R18 이 거부할 남의 공유 체크아웃에서. 그 거부들은 정확히 그런 실행을 막으려고 있는 것이므로, 순서가 뒤집히면 게이트가 자기가 막으려던 일을 자기가 한다. 실행 위치도 같다 — 겨냥하는 실패가 "사용자 체크아웃에서는 돌고 대상에서는 안 되는 명령"이므로, 기동 디렉터리에서 돌리면 검사가 **대상이 아니라 런처를 검사**하게 되어 잡으려던 사례를 정확히 놓친다. 둘 다 완료 기준에서 따로 고정한다(독립 검증 F3 — 코드는 맞았으나 테스트가 없어 변이가 살아남았다).

  **거부 메시지는 두 갈래를 가른다**(R5-1 `kind`). `unrunnable` 은 "실행조차 못 했다"이고 처방은 러너·환경 확인(gitignore 된 `.venv`·`node_modules`)이다. `timeout` 은 **실행은 됐고 끝나지 않은 것**이라 그 처방이 오답이다 — 상한만큼 기다린 사용자에게 "명령이 없다"고 말하는 셈이고, 맞는 처방은 스위트 범위 축소나 지연 원인 해소다. 증거가 없다는 결론과 거부 판정은 두 갈래가 같으므로 **갈리는 것은 메시지뿐이다.**

  **대가는 기동 지연 1회분**(첫 반복 전에 스위트를 한 번 돈다. 타임아웃 갈래에서는 그 대가가 상한만큼이다 — 그래서 메시지가 더 정확해야 한다). 우회 플래그는 두지 않는다 — R16의 예산 리셋 플래그·R18의 우회 플래그를 기각한 것과 같은 이유다.

### 멀티 엔진 (driver.py — Claude Code CLI + Codex CLI)

- **R13 (엔진 추상화 + 역할별 엔진)**: 드라이버는 헤드리스 세션을 두 엔진 중 하나로 돌린다 — `claude`(기본) 또는 `codex`. 엔진은 역할별로 갈릴 수 있다: `resolve_engine(cfg, readonly)` = `(verify_engine if readonly else implement_engine) or engine`. 즉 `--engine`이 균일 기본, `--implement-engine`/`--verify-engine`가 역할 오버라이드다("구현=claude, 검증=codex" 요구를 이걸로 충족). 티어 모델 해석(R6)은 엔진과 직교로 유지된다(각 엔진의 `--model`/`-m`에 전달).
- **R14 (엔진별 표면·안전 매핑)**: 각 엔진의 헤드리스 인자·출력·안전 게이트를 아래로 고정한다. **bypass 계열은 두 엔진 모두 절대 금지**(§3).

  | | Claude(`claude`) | Codex(`codex`) |
  |---|---|---|
  | 헤드리스 | `-p <prompt>` | `exec <prompt>` |
  | 편집 세션 게이트 | `--permission-mode acceptEdits` + `--setting-sources project`(R3-1) + `--allowedTools`(SAFE_ALLOW+extra) + `--disallowedTools`(DESTRUCTIVE) | `--sandbox workspace-write` + `--skip-git-repo-check` + `-C <project>` |
  | 검증 세션(readonly) | 위와 동일한 모드·설정 소스 + `READONLY_ALLOW` + disallow | `--sandbox read-only`(쓰기 자체 차단) |
  | 모델 | `--model <M>` | `-m <M>` |
  | 출력 취득 | `--output-format json` → stdout `{result,total_cost_usd}` | `-o <파일>` → 최종 메시지 텍스트(비용 미제공 → 0) |
  | 금지(bypass) | `--dangerously-skip-permissions` | `--dangerously-bypass-approvals-and-sandbox` |

  Codex는 fine-grained 도구 목록이 없어 sandbox 레벨이 게이트다(비목표의 잔여 갭 참조). `--allow-extra`는 Claude 전용(Codex는 sandbox라 무의미 — 무시). **하네스 로드 차이(F1)**: Codex는 쓰기를 프로젝트에 confine하려 `-C <project>`로 실행되므로 하네스 루트 AGENTS.md가 자동 로드되지 않을 수 있다(Claude 경로는 cwd=하네스 루트로 항상-온 로드 — §12). 따라서 Codex 경로에서 필수 게이트는 **프롬프트에 임베드된 anchor·instructions·untrusted 봉투**가 나르고, 하드 게이트는 **sandbox**가 담당한다(비목표 "오케스트레이션 대체 아님"의 하네스 자동로드 가정은 Claude 엔진 한정).

- **R15 (엔진 기본값 선택 — SKILL.md)**: 기동 세션의 CLI에 기본 엔진을 맞춘다 — Codex 세션이 기동하면 `--engine codex`, Claude 세션이면 기본(`claude`). 불확실하면 사용자에게 확인한다. 사용자가 역할별 엔진을 명시하면(구현/검증) 그대로 `--implement-engine`/`--verify-engine`로 전달한다.

## 인터페이스 / 설계 개요

```
사용자 ── /autoloop start <스펙> ──▶ SKILL.md(발사대: 검사·기동·안내)
                                        │ nohup
                                        ▼
                         driver.py (세션 외부 프로세스)
                           ┌──────── 반복 ────────┐
                           │ STOP? → 안전 종료      │
                           │ 프롬프트(앵커+노트+증거) │
                           │ claude -p (acceptEdits │
                           │   +allow/disallow)     │──▶ 대상 프로젝트 편집·커밋
                           │ 상태 블록 파싱          │
                           │ test-cmd 독립 실행      │
                           │   → green/red/error 분류│
                           │ carryover.md·로그 갱신  │
                           │ state.json 체크포인트    │
                           │ 정지 판정(R7 7조건)     │
                           └───────────────────────┘
                           done 주장 → reviewer 검증 반복(PASS/BLOCK, 래칫 확인)
                           재기동 → state.json 로드 → 멈춘 게이트 상태로 이어서
```

- 드라이버 cwd는 하네스 루트(하네스 항상-온 로드 — §12 세션 시작 관행), 대상 프로젝트는 `--project`로 지정하고 프롬프트에 명시한다.
- 의존성: Python 3 표준 라이브러리만(§16 사다리 5단 — 새 의존성 금지). Claude Agent SDK는 쓰지 않는다 — permission callback의 정밀함보다 무의존이 이 규모에 맞고, allow/disallow 목록으로 동등한 경계를 긋는다.
