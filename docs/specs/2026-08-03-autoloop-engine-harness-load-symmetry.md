# 스펙: autoloop 무인 세션의 엔진 간 하네스 로드 비대칭 해소

- 날짜: 2026-08-03 / 상태: 구현됨(ADR 048·구조화 오케스트레이션 스펙으로 해결)
- 관련: `docs/specs/2026-07-19-autoloop-driver.md`(선행 스펙), `.agents/skills/autoloop/scripts/driver.py`, 루트 AGENTS.md §12·§3

> **해결됨(2026-08-19; 2026-08-20 개정)**: 현재 Codex는 task worktree를 `-C` 경계로 유지하고, 루트 자동 로드를 전제로 삼지 않은 versioned bounded orchestrate contract를 모든 역할 prompt에 주입한다. `--ignore-user-config`, network false, noninteractive approval, core 환경 상속도 driver가 고정한다. Codex writer는 격리된 `workspace-write` worktree에서 native로 실행하며 파괴·경계 변경 diff는 fan-in 전에 차단한다. 아래 목표·요구사항·미해결 질문은 2026-08-03의 문제 기록이며 현재 구현·회귀 기준은 `2026-08-19-autoloop-orchestration-runtime.md` R7·C2·C6과 ADR 048이다.

## 배경

autoloop 드라이버는 무인 반복 세션을 두 엔진(`claude` / `codex`) 중 하나로 돌린다. **두 엔진이 세션에 넘기는 작업 위치가 서로 다르고, 그 결과 각자 반대쪽 절반만 갖는다.**

실측(`driver.py`, 2026-08-03 HEAD `33a2e33`):

| | Claude 경로 | Codex 경로 |
|---|---|---|
| 프로세스 `cwd` | `self.cfg.cwd` (`:628`) | `self.cfg.cwd` (`:650`) |
| 세션이 보는 작업 루트 | 프로세스 `cwd` = 하네스 루트 | `-C cfg.project` (`:327`) = **프로젝트** |
| 루트 하네스 항상-온 로드(§12) | 로드됨 — `--setting-sources project`(`:310`)로 의도적으로 유지 | **로드 안 됨** |
| 프로젝트 트리 도달 | 하위 디렉토리로 도달 | 작업 루트 자체 |
| 쓰기 범위를 가두는 수단 | 도구 허용 목록(`SAFE_ALLOW`·`DESTRUCTIVE_DISALLOW`, `:55`·`:69`) | 샌드박스 = workspace(`--sandbox workspace-write`, `:326`) |

`cfg.cwd`는 기동 시점 `os.getcwd()`(`:889`), `cfg.project`는 `--project`(기본 `.`)의 `os.path.abspath`(`:865`·`:886`)다. 표준 경로 규약에서 `project/<이름>/`은 하네스 루트의 하위 디렉토리이므로, **Claude 세션은 프로젝트에 그대로 도달한다.**

두 가지가 여기서 나온다.

1. **선행 문제 서술의 부분 정정.** 이월 노트는 "무인 세션이 대상 project 트리에 닿지 못한다"고 적었다. **파일 도달에 한해서는 거짓이다** — 표준 경로 규약에서 프로젝트는 루트 하위이므로 Claude 세션이 경로로 읽고 쓴다. **그러나 실행 표면 근거는 그대로 남는다**: `--add-dir`이 없고, `SAFE_ALLOW`에 `Bash(cd:*)`가 없어(`:55`~`:64`) 세션이 프로젝트 디렉토리에서 명령을 돌릴 수 없다 — 테스트·빌드는 하네스 루트에서 실행된다. 즉 정정되는 것은 "파일에 닿지 못한다"이지 "프로젝트에서 작업할 수 있다"가 아니다. 프로젝트가 루트 **밖**인 경우는 두 축 모두 정의되어 있지 않다(조용히 반쪽으로 돈다).
2. **실제 결함은 반대 방향이다.** Codex 무인 세션은 루트 하네스의 규칙·가드레일을 **한 줄도 읽지 않은 채** 구현을 수행한다. 이는 루트 AGENTS.md §7 2항이 하위 하네스 부재에 대해 정지를 거는 것과 같은 종류의 상태 — 덜 아는 것이 아니라 규칙 없이 도는 것 — 이며, 무인이라 사람이 알아챌 지점도 없다.

**대칭화가 한 줄이 아닌 이유**: `-C`를 하네스 루트로 올리면 Codex는 항상-온을 얻지만, `workspace-write` 샌드박스의 쓰기 범위가 workspace(=작업 루트)이므로 **무인 세션의 쓰기 가능 영역이 프로젝트에서 하네스 루트 전체로 넓어진다.** 로드 대칭과 격리 유지가 서로 반대로 당기므로 §3급 판단이고, 그래서 스펙이 선행한다.

## 목표

1. 두 엔진의 무인 세션이 **모두** 루트 하네스 항상-온 문서를 로드한 상태로 구현을 수행한다.
2. Codex 무인 세션의 쓰기 가능 범위가 현행(프로젝트 트리)보다 **넓어지지 않는다**.
3. 프로젝트가 하네스 저장소 트리 밖일 때 두 엔진 모두 **착수 전에 멈추고 사유를 낸다** — 정의되지 않은 반쪽 동작이 사라진다. 이 판정은 드라이버를 **어디서 기동했는지에 좌우되지 않는다**.
4. 각 엔진의 인자 구성과 위 세 성질이 회귀 테스트로 고정된다.

## 비목표

- **샌드박스 세부 제어** — fine-grained denylist 부재와 설치처 `~/.codex/config.toml`의 `[sandbox_workspace_write]`가 네트워크 기본값을 덮을 수 있다는 점은 선행 스펙의 미해소 갭(R3-2)이며 이번 범위가 아니다. 근거: 런타임 미측정 상태로 `-c`를 걸면 조용히 무효가 될 수 있다는 판단이 이미 기록돼 있고, 이번 변경은 그 판단을 뒤집을 새 측정을 가져오지 않는다.
- **Claude 도구 허용 목록 재설계** — `SAFE_ALLOW`/`DESTRUCTIVE_DISALLOW`의 내용은 건드리지 않는다. 이번 축은 *어디서 도는가*이지 *무엇을 할 수 있는가*가 아니다.
- **Windows** — 선행 스펙과 동일하게 macOS·Linux만 보장 범위다(ADR 031).
- **엔진 선택 정책** — 어느 역할에 어느 엔진을 쓸지는 `resolve_engine`의 기존 규칙 그대로다.

## 요구사항

- **R1**: Codex 구현 세션이 루트 하네스의 항상-온 문서를 로드한 상태로 실행된다.
- **R2**: R1을 만족시키면서 Codex 세션의 **쓰기 가능 경로는 프로젝트 트리 이하로 유지**된다. R1의 수단이 쓰기 범위를 넓히는 형태라면 그 수단은 채택하지 않는다.
- **R3**: `cfg.project`가 **하네스 저장소 트리** 안이 아니면 **드라이버가 첫 세션을 띄우기 전에 종료**하고, 어느 경로가 어느 루트 밖인지 명시한다. 판정은 심볼릭 링크를 푼 뒤(`os.path.realpath`) 수행한다 — 링크로 우회하면 검사가 무의미해진다.
- **R3-1**: 그 트리의 기준점은 `cfg.cwd`(`os.getcwd()`)가 **아니라** `harness_repo_common_dir()`다. `cfg.cwd`는 사용자가 어디서 기동했는지일 뿐이라 하위 프로젝트 안에서 기동하면 그 저장소가 "루트"로 잡히고, R3가 자기 자신에게 무의미하게 통과한다. 드라이버 파일의 위치는 하네스 저장소 안이라는 것이 설치 구조상 보장된다. **이 기준점은 이번에 새로 고르는 것이 아니라 `driver.py`가 이미 같은 이유로 채택해 둔 것이다**(`harness_repo_common_dir()` docstring — 선행 독립 검증 F1 실측: `cfg.cwd`를 쓰면 "게이트가 통째로 무효"). 같은 파일 안에서 두 기준점이 공존하면 하나는 반드시 틀린다.
- **R4**: R3의 종료는 **실패**이며 성공으로 위장하지 않는다(0이 아닌 종료 코드, 상태 파일에 사유 기록).
- **R5**: 두 엔진의 인자 구성이 회귀 테스트로 고정된다 — 인자에서 작업 루트를 결정하는 부분을 제거·반전하는 변이가 테스트를 실패시킨다.
- **R6**: 변경 커밋은 §13-4에 따라 재실행한 회귀 시나리오를 커밋 메시지에 명시한다. 드라이버는 무인 세션의 권한과 실행 여부를 판정하는 게이트다.

## 인터페이스 / 설계 개요

바뀌는 경계면은 셋뿐이다.

- **`build_codex_args(cfg, prompt, readonly, out_file)`** — 작업 루트를 결정하는 `-C` 인자. R1과 R2를 동시에 만족시키는 형태만 허용된다.
- **`build_claude_args(cfg, prompt, readonly)`** — 현행 유지가 기본. R3가 성립하면 프로젝트는 항상 루트 하위이므로 추가 인자가 필요 없다.
- **신설 사전 검사** — 드라이버 기동 경로(`main`)에서 세션 루프 진입 **전에** 1회 수행하는 경로 포함 관계 판정. 반환이 아니라 종료로 처리한다(R4).

프롬프트·상태 파일·이벤트 스키마는 바뀌지 않는다.

## 완료 기준 (테스트 가능한 형태)

- [ ] C1 (R1·R2): Codex 인자 구성 함수의 반환값이 **루트 하네스 항상-온 문서가 로드되는 작업 루트**를 지정하면서, 동시에 쓰기 범위를 프로젝트 트리 이하로 두는 형태다 — 두 성질을 각각 별개 단언으로 검사한다(한 단언이 두 성질을 겸하면 하나가 깨져도 통과한다).
- [ ] C2 (R2): Codex 세션의 쓰기 가능 경로를 프로젝트 트리 밖(예: 하네스 루트의 추적 파일)으로 넓히는 인자 조합을 넣으면 테스트가 실패한다.
- [ ] C3 (R3·R3-1): `--project`가 하네스 저장소 트리 밖 경로일 때 드라이버는 **세션을 한 번도 띄우지 않고** 종료한다 — 세션 실행 함수가 호출되지 않았음을 단언한다(로그 문구가 아니라 호출 여부로 판정한다).
- [ ] C4 (R3): 심볼릭 링크로 루트 안을 가리키는 바깥 경로도 C3와 같이 종료한다(`realpath` 적용 확인).
- [ ] C4-1 (R3-1): **하위 프로젝트 디렉토리 안에서 드라이버를 기동해도** 판정 결과가 달라지지 않는다 — 기준점이 기동 위치를 따라가지 않음을 고정한다(`cfg.cwd`를 기준점으로 되돌리는 변이가 이 케이스를 실패시킨다).
- [ ] C5 (R4): C3의 종료 코드가 0이 아니고, 상태 파일에 사유가 남는다.
- [ ] C6 (R5): 두 엔진 각각에 대해, 인자에서 작업 루트 지정을 제거하거나 서로 뒤바꾸는 변이가 최소 1건의 테스트를 실패시킨다(변이 검정을 실제로 돌려 확인한다).
- [ ] C7 (R3): 표준 경로 규약(`project/<이름>/`)에서는 사전 검사가 통과하고 기존 동작이 그대로 유지된다 — 이 변경이 정상 경로를 막지 않음을 고정한다.

## 미해결 질문

- **R1의 수단이 미정이다.** Codex가 작업 루트 밖의 프로젝트 문서를 로드하는 수단이 있는지, 있다면 그것이 샌드박스 쓰기 범위와 독립인지는 **이 세션에서 판정하지 않는다** — Codex 런타임 동작은 실행해 봐야 알 수 있고, 그 판정은 이 하네스가 자기 근거로 삼을 수 있는 종류가 아니다(같은 이유로 선행 스펙도 `-c` 고정을 보류했다). 따라서 구현 착수 전에 **설치처에서 실측**해야 하고, 실측 결과에 따라 셋 중 하나로 확정한다: ① 문서 로드 경로를 따로 지정할 수 있다 → 그것을 쓴다(R2 그대로 만족) ② 없다 → `-C`를 루트로 올리는 대신 **루트 항상-온 내용을 프롬프트에 실어 보낸다**(쓰기 범위 불변, 로드는 근사) ③ 둘 다 불가 → Codex를 구현 역할에서 제외하고 검증 역할로만 둔다(로드 없이 도는 상태를 남기지 않는다).
- ②를 택할 경우 프롬프트 크기가 세션당 고정 비용으로 더해진다. 그 비용을 감수할지는 실측된 바이트 수를 보고 판단한다 — 지금 추정치를 적지 않는다.
- **「대칭화가 한 줄이 아닌 이유」의 샌드박스 서술도 미측정이다.** `-C`를 올리면 `workspace-write`의 쓰기 범위가 그 작업 루트로 넓어진다는 것은 문서화된 동작에서 온 추론이지 이 설치처에서 재 본 값이 아니다. 위 R1 수단과 **같은 종류의 Codex 런타임 주장**이므로 같은 취급을 받아야 한다 — 한쪽만 보류하고 다른 쪽을 단정하면 보류의 기준이 없어진다. R1 실측 때 이것도 함께 확인한다(루트에서 `-C`로 띄운 세션이 프로젝트 밖 파일을 실제로 쓸 수 있는가).
- 이 스펙은 훅이 아니라 스킬 스크립트를 대상으로 하므로 doc-writer의 루트 훅 교차 플랫폼 체크리스트는 적용되지 않는다. 다만 R3의 종료 경로는 콘솔 인코딩을 타므로, 구현 시 기존 드라이버의 출력 처리 방식을 그대로 따른다.
